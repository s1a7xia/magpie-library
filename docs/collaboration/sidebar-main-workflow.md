Lead: 这套分工合理。关键不是谁都能改文档，而是事实、决策、验收各有唯一归属。

## A 结论先放这
```callout ok 合理，但要设边界
- **侧边栏**负责讨论、比较、收口方案。
- **主线程**负责执行、取证、更新状态。
- **状态文档**只反映事实，不承载全部讨论。
- **你**保留最终拍板权。
```

## B 一条任务的闭环
```flow LR
[侧边栏 方案与验收] -> [主线程 执行与取证]: 任务包
[主线程 执行与取证] -> [(STATUS.md)]: 完成即更新
[(STATUS.md)] -> [侧边栏 方案与验收]: 只读审阅
[侧边栏 方案与验收] -> [你 最终拍板]: 有偏差才升级
[你 最终拍板] -> [(DECISIONS.md)]: 确认后追加
[(DECISIONS.md)] -> [主线程 执行与取证]: 下一轮约束
```

## C 状态文档不是完整会议纪要
```callout info 拆开记录
`STATUS.md` 只回答“现在到哪”。
“为什么这么定”应进入 `DECISIONS.md`。
```

| 文档 | 唯一写手 | 回答的问题 | 写法 |
|------|----------|------------|------|
| `STATUS.md` | 主线程 | 当前到哪 | 覆盖更新 |
| `DECISIONS.md` | 侧边栏 | 为何这样定 | 追加记录 |
| `TASKS/<id>.md` | 主线程 | 这次做什么 | 每任务一份 |

## D 哪些做法合理
| 做法 | 判断 | 原因 |
|------|------|------|
| 侧边栏发散、比较、收口 | ok | 讨论留在一个地方 |
| 主线程执行并回报证据 | ok | 施工队掌握现场 |
| 主线程只照做，不做判断 | warn | 验收偏差会放大 |
| 两个会话实时同步聊天 | no | 会话本来就独立 |
| 两边同时改 `STATUS.md` | no | 会覆盖，出现两个真相 |

## E 一条硬规则：唯一写手
```callout warn 同一份文件只设一个写手
并发修改会覆盖内容。冲突后，状态可能倒退。
代码、证据、结论也可能互相矛盾。
```

- 主线程写事实，侧边栏不改写事实。
- 侧边栏写决策，主线程不回填理由。
- 你改优先级或验收标准，两边都要知道。

## F 最小落地
1. 侧边栏发任务包：目标、范围、验收。
2. 主线程复述验收标准，再开工。
3. 主线程更新 `STATUS.md`，附改动证据。
4. 侧边栏只读审阅，不直接改状态。
5. 新决策写 `DECISIONS.md`，并回链任务。
6. 返工仍由主线程执行和更新状态。

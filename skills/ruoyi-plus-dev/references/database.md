# Database Reference

用于表结构、SQL、字典、参数和菜单数据。先读 [common.md](common.md) 的流程、复用检查和交付门禁。

## 先复用框架数据

- 用户、部门、角色、岗位、字典、参数、文件等先查 `sys_user`、`sys_dept`、`sys_role`、`sys_dict_type`、`sys_dict_data`、`sys_config`、`sys_oss` 等现有表，按明确语义引用其 ID 或编码。
- 不为同义组织、状态或配置另建体系；不把可在 `sys_config` 管理的运行参数做成新表。
- 菜单、按钮权限和字典变更要有可执行的数据脚本；前端权限字符、后端 `@SaCheckPermission` 与 `sys_menu` 数据保持一致。

## 表与字段

- 表和列使用小写下划线；Entity 字段、DDL、BO/VO 和前端类型的命名映射保持一致。
- 继承 `BaseEntity` 时对齐五个审计字段：`create_dept`、`create_by`、`update_by` 为 `Long`，`create_time`、`update_time` 为 `LocalDateTime`。创建信息不等于业务归属或外部事件时间。
- 主键不由 `BaseEntity` 提供；`@TableId` 策略必须与 DDL 和 ID 生成方式一致。全局 `ASSIGN_ID` 与显式自增按目标表选择，前端传输保留精度。
- `status`、`del_flag`、`version`、`remark`、`tenant_id` 均按需求添加，不假设基类自带。启用逻辑删除、乐观锁或租户字段时，要同时接入对应机制。
- 身份、状态、权限、唯一键、常用筛选与排序列落成真实列；需要 SQL 查询的字段不要只藏在 JSON 中。
- 审计自动填充、DDL 默认值和自定义 SQL 分别核对；时间类型、时区、字典值和前后端契约一致。

## JSON 的边界

- 可变低频详情可以放 JSON；类型、序列化器和数据库方言要匹配。
- 若 JSON 需要频繁筛选、排序、聚合、唯一约束或数据权限，应拆成列或独立表。
- 数据库脚本不要绑定单一数据库专属 JSON 语法；目标支持多种数据库时，分别验证实际写法。

## 键、约束与并发

- 明确业务唯一性、外键/引用关系、可空性、默认值和索引；唯一性优先由数据库约束保证，不能只靠应用先查后写。
- 常用查询列建立索引，避免无界模糊查询；大字段和 JSON 不盲目建普通索引。
- 明确删除与历史保留规则、并发更新条件和冲突处理；允许清空的字段要与 MyBatis-Plus 更新策略一致。
- 业务归属字段与 `create_dept/create_by` 分开；数据范围接入实际业务字段，并覆盖查询、导出和写操作。

## SQL 交付

- 表结构、字典、系统参数和菜单变更提供配套脚本。该工程常见入口为 `script/sql/`，并按 `oracle/`、`postgres/`、`sqlserver/` 等实际方言目录维护。
- XML 和脚本避免绑定单一数据库的专属语法或反引号；确需方言差异时分别提供并说明。
- 脚本先做只读核对，再按授权执行。数据库写入、生产执行和批量变更不因本地连接可用而自动获准。
- 提交前核对脚本可重复执行性、默认值、字符集/排序规则、索引名和初始化数据是否与目标版本一致。

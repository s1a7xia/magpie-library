# Implement

实现用户指定的 spec、ticket 或当前对话中已经定稿的工作。不要重新访谈、重新设计或提出替代方案；上游已经确认的内容就是本技能的输入。

如果用户传入 ticket 引用，先从项目配置的 issue tracker 读取，并在开始前列出它的标题。引用有歧义时先问清楚，不要猜测编号。只有 spec 且工作很小时，可以直接按 spec 实现；工作跨越多个独立切片时，先用 `$to-tickets` 拆票，再每次实现一个 ticket。

## 边界

- 一次调用只处理一个 ticket，或一个最小充分的可交付切片。不要顺手把多个 ticket 合并成一次大改。
- 默认在当前 Codex 会话和当前工作区实现。不要创建 worktree、启动子代理或并行会话。
- 不自动创建或切换分支，不自动提交、推送、合并、创建 PR 或修改外部 Issue。提交和外部写入仅在当前任务明确授权时执行。
- 实现不等于测试授权。只有当前任务明确要求测试、构建、类型检查或页面验证时，才运行对应最小范围；未授权时只做实现和静态核对，并如实标明未验证。
- 只有当前任务明确要求 `$code-review` 时才审查。不要因为实现完成就自动调用它。
- 修改 RuoYi-Vue-Plus 的 `ruoyi-modules/ruoyi-*` 后端或 `plus-ui-React/src` 对应代码前，读取 `ruoyi6` 的 `SKILL.md`。讨论或修改尚未确定的持久化对象、字段、关系、状态或迁移时，先读取 `database-design` 的 `SKILL.md`。

## 流程

1. 读取 spec、tickets、项目 `AGENTS.md`、术语表、ADR、状态文档和相关代码。确认当前 ticket 的目标、验收、数据/API/权限影响和 blocking edges。
2. 找出预定的 seam 和最小纵向切片。优先复用现有模块、接口、组件、字典、配置和相邻业务实现；不为假想需求增加抽象。
3. 在当前会话实现该切片。遵循项目现有命名、分层、异常处理、日志和前端写法；保护用户已有改动。
4. 核对实际 diff、调用关系和受影响的契约。发现规格缺口时停止扩大实现，记录阻塞决策；不要用新的设计悄悄替换已确认方案。
5. 只同步本次实际影响的现有文档。实现完成和验收通过分开记录；不要自动关闭 ticket 或把未运行的检查写成已通过。
6. 报告已完成的行为、关键变化、ticket 状态、实际执行的验证和未验证边界。剩余 ticket 或需要授权的提交、推送、审查与发布单独列出。

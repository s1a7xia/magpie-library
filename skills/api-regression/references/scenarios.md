# 场景与断言

## 设计纵向场景

每个场景写清：

- 前置业务事实和参与身份；
- 动作链和每个角色的权限边界；
- 预期终态及必须保持不变的旧事实；
- 关键拒绝分支；
- 证据来源和清理方式。

按需求或验收手册定义预期，不从当前响应反推“正确答案”。只覆盖有业务意义的角色、状态和异常；不机械复制全部 CRUD。

## 断言层次

同时检查：

1. HTTP 状态和传输失败；
2. 应用业务码、错误码和响应结构；
3. 业务查询接口返回的外部可见结果；
4. 使用已连接的数据库只读 MCP 时，事务、审计和跨表一致性；按 [数据库只读核对](database-verification.md) 执行；
5. 拒绝请求后数据确实未改变。

数据库断言不能替代公开业务行为；业务接口成功也不能证明后台任务、外部集成或页面完成。关键闭环至少对账“API 返回对象 → 精确 ID 查询 → 终态/旧事实”三层，不能只凭页面显示或单次 HTTP 200 判断。

## 身份和数据

- 每个角色独立会话，真实验证认证、鉴权、组织和租户过滤。
- 每次运行使用唯一 run ID，使用本轮响应中的 ID，不硬编码历史样本。
- 共享资源流程串行；只有数据、会话和外部资源独立的场景才并行。
- 异步任务设置明确终态和截止时间，按真实调度状态轮询，不用固定长 sleep。
- 拒绝分支覆盖最关键的越权、非法状态、重复提交或“审批不能改已生效结果”。

## Mock 边界

不 mock 认证、鉴权和核心事务来宣称闭环。必须 mock 第三方时，只报告内部流程通过；真实集成单列为未验证。禁止向真实客户发送测试通知、触发未授权扫描或其他外部副作用。

# Development Workflow

这是唯一的通用工程入口。用户描述目标即可，不要要求用户选择或手动调用阶段名称。先读当前请求、项目 `AGENTS.md`、相关代码和已有文档，再在内部选择最短路径；只读请求不得擅自进入实现。

| 任务信号 | 内部阶段 | 边界 |
|---|---|---|
| 明确的小修、局部改动 | 直接实现 | 读受影响代码和调用方，最小修改 |
| 报错、崩溃、回归、行为异常 | `debug` | 先定位根因，再修直接受影响路径 |
| 需求模糊、方案未定、跨模块改造 | `think` | 先形成目标、边界和验收项 |
| 方案需要严格挑战、边界或取舍验证 | `grill` | 只问会改变结果的决策 |
| 已确认方案需要独立交付切片 | `story` | PRD/Issue 都是可选的记录载体 |
| 实现已确认需求或切片 | `implement` | 按现有约定直接实现 |
| 技术选型、版本差异、外部框架行为 | `research` | 只查与当前决策有关的权威事实 |
| 要求审查、准备合并或发布 | `review` | 默认主代理只读审查 |
| 明确要求初始化项目 AI 约定 | `setup-project` | 仅在用户明确要求时使用 |

默认闭环：

```text
目标与验收 → 取证 → 方案/切片（仅必要时）→ 实现或修复
  → 验证（仅按授权）→ 审查（按风险）→ 结果与未验证边界
```

不要为了“完整”加载全部阶段。小任务可以跳过方案、PRD、Issue 和独立审查；缺少这些记录不阻塞开发。

## 阶段模块

阶段目录是同级的内部模块。只有路由命中时才读取对应 `SKILL.md`，确有需要再读它的 `REFERENCE.md` 或其他参考文件：

- `../think/SKILL.md`
- `../research/SKILL.md`
- `../grill/SKILL.md`
- `../story/SKILL.md`
- `../implement/SKILL.md`
- `../review/SKILL.md`
- `../debug/SKILL.md`
- `../setup-project/SKILL.md`
- `../rules/entry-protocol.md` 以及阶段明确引用的共享规则

阶段名称不是用户命令。读取阶段文档后继续完成当前任务，不要输出“请运行 /think”或“请再开 review”。

## 业务规范叠加

命中以下场景时，在设计或实现前加载相应业务 Skill；项目专用规范优先于通用阶段方法：

| 场景 | 必须叠加 |
|---|---|
| 尚未决定数据模型：新表、拆并表、关系、唯一性、生命周期、删除语义、JSONB 建模或结构性迁移 | `database-design` |
| 实际修改 RuoYi-Vue-Plus 6.x + plus-ui-React 代码、接口、权限、菜单、字段链路或已批准的数据落表 | `ruoyi6` |
| 用户明确要求深度视觉设计或整页改版 | `frontend-design` |
| 用户明确要求 API 回归、多账号权限或数据库终态验证 | `api-regression` |
| 用户明确授权独立审查/委派，或要求 Alma 会话查看、通知、审批转达和协调 | `team-orchestration` |

数据库按两层处理：

1. 模型尚未决定时先加载 `database-design`，确定表、关系、身份、唯一性、生命周期、删除、查询和迁移契约。
2. 契约已确认后，由 `ruoyi6/references/database.md` 负责 RuoYi/PostgreSQL 的字段落点、Entity/BO/VO/TS/Menu 链路和增量脚本。普通字段、索引或字典实现不重新跑建模；发现契约冲突才回到 `database-design`。

新增持久化表仍需用户对列明表名明确同意；模型设计、编写脚本和执行数据库变更分别授权。

## 文档与 Git

- 只更新本次行为实际影响的现有文档；不默认新建 brief、handoff、PRD、Issue 或控制台账。
- 改动后检查实际 diff，区分产品代码、测试、文档和用户已有改动。
- 提交、推送、合并、发布和数据库变更分别按当前授权执行；“按闭环做”不自动扩大这些权限。
- 交付说明用户可见结果、实际执行的验证、未验证边界和必要的 Git 状态；不把编译通过或工具连通当作业务验收。

# Development Workflow

这是本项目唯一的通用工程工作流入口。用户描述目标和结果即可，不要要求用户选择或手动输入 `think`、`review` 等阶段名称。阶段文档是内部方法模块，不是必须由用户逐步触发的命令。

## 基本契约

- 先读当前用户请求、项目 `AGENTS.md`、相关代码和已有项目文档，再判断任务是否需要改代码。只读请求、需求整理和方案讨论不得擅自进入实现。
- 当前请求的目标和验收标准优先于内部阶段文档；项目约定和适用的业务 Skill 优先于通用阶段方法。阶段文档里的 `/think`、`/review`、`Next: Run ...` 等文字只表示内部转场，不得转成要求用户手动执行的下一步。
- 默认只保留一个工作区写入者。仅在用户明确授权委派时，调查、审查和测试才交给只读子代理；产品代码、文档和 Git 收尾仍由主代理统一处理。
- 读证据，不猜实现。能从代码、测试、配置、数据库或项目文档得到的事实先自行查清；只有会实质改变范围、数据规则或授权的问题才问用户。
- 保留用户已有改动。不得用 `git reset`、`git clean`、覆盖文件或回滚操作清理无关内容。
- 测试不是默认动作。普通实现、修复或重构不自动运行测试，也不自动编写测试；只有当前请求明确要求测试、验收或回归证明时才执行相应范围。用户未要求测试时，不反复询问，交付时说明未运行测试即可。

## 自动路由

先在内部判断任务属于哪一类，再读取必要模块。不要为了“完整”而加载所有阶段。

| 任务信号 | 内部路径 | 执行边界 |
|---|---|---|
| 单文件小修、明确错字、样式微调、已定位的局部改动 | 直接实现或 `debug` 修复 | 读受影响代码和调用方，最小修改，只做相关检查；不建 PRD/Issue |
| 报错、崩溃、回归、测试失败、行为异常 | `debug` | 先定位根因并做最小修复；需要测试或回归证明时再按授权执行 |
| 需求模糊、多个方案、跨模块改造、新业务模块 | `think`；需要设计挑战时接 `grill`；需要多切片时接 `story` | 先形成目标和验收标准；简单任务不写正式 PRD |
| 已有明确方案或多个可独立交付的切片 | `story` → `implement` | 只有项目已配置 Issue tracker 或用户要求时才创建 Issue；否则用对话或现有项目文档承接 |
| 纯技术选型、版本适配、外部框架行为 | `research`，必要时接 `think` | 只查与当前决策有关的事实；不要用调研替代代码取证 |
| 实现已有需求或已批准的切片 | `implement` | 按契约直接实现；普通实现不自动补测试 |
| 改动完成、准备合并或发布 | `review` | 普通改动做聚焦自查；用户明确授权第二视角或委派时做独立审查，其余由主代理聚焦自查 |
| 用户要求初始化或调整项目约定，或授权任务确实依赖缺失约定 | `setup-project` | 沿用已有项目约定；缺少 docs/agents 本身不触发，不作为开发前置条件 |
| 用户明确要求“只整理需求/先讨论/不改代码” | `think` 或 `research` 后停止 | 输出目标、边界、验收项和待决问题，不写产品代码 |

路由后的默认闭环是：

```text
目标与验收 → 取证 → 方案/拆解（仅必要时）
  → 实现或修复 → 验证（仅按授权）→ 审查（按风险）
  → 结果与未验证边界
```

如果任务很大或风险很高，可以在闭环中增加阶段；如果任务很小，允许跳过方案、Issue、正式 PRD 和独立审查。阶段数量服务于正确交付，不是交付目标。

## 阶段模块

本文件所在的 `skills/dev-workflow/` 与阶段模块同级。需要某个阶段时，读取对应目录的 `SKILL.md`，只在确有需要时再读它的 `REFERENCE.md` 或其他参考文件：

- `../think/SKILL.md`
- `../research/SKILL.md`
- `../grill/SKILL.md`
- `../story/SKILL.md`
- `../implement/SKILL.md`
- `../review/SKILL.md`
- `../debug/SKILL.md`
- `../setup-project/SKILL.md`
- `../rules/entry-protocol.md` 以及阶段明确引用的共享规则

这些目录是内部实现，不应作为用户的并列技能菜单。读取阶段文档后继续完成当前任务，不要输出“请运行 /think”或“请再开 review”。

## 业务规范叠加

通用工作流只负责工程阶段，不替代用户的业务编码规范。命中以下场景时，必须在设计或实现前加载相应业务 Skill，并让其约束覆盖通用阶段规则：

| 场景 | 必须叠加 |
|---|---|
| 新建/修改表、字段、约束、索引、删除语义、迁移或 JSONB 边界 | `database-design` |
| 实际 RuoYi-Vue-Plus 6.x + plus-ui-React 代码、接口、权限、菜单或字段链路 | `ruoyi6`，数据库部分同时 `database-design` |
| 用户明确要求深度视觉设计或整页改版 | `frontend-design`（未分发时按项目现有视觉规范执行，并说明未加载能力） |
| 用户明确要求 API 回归、多账号权限或数据库终态验证 | `api-regression`（仅在实际分发时加载），优先复用现有测试入口 |
| 用户明确授权独立审查/委派，或要求 Alma 会话查看、通知、审批转达和协调 | `team-orchestration`，仅在实际分发时加载；否则遵循项目 `AGENTS.md` 和全局指令 |

同名或项目专用业务规范存在时，以项目当前版本为准；不要把这些规则复制进通用插件，也不要用通用原则覆盖已确认的业务契约。

数据库工作是硬门槛：**任何新增或修改持久化模型的动作都必须加载 `database-design`**，包括新表、加字段、约束、索引、迁移，以及字典/参数与数据库字段的绑定。需求已批准不等于数据库检查完成；它只意味着走轻量增量契约核对，不再重新讨论已确认的产品方案。

分级执行：已批准任务给现有表加普通字段、补索引或补字典项时，只核对复用位置、字段语义/类型/可空/默认值、实体与前端字段链路、迁移与回滚，不重做完整业务判型；新表、改关系/唯一性/删除语义/生命周期/历史策略、JSONB 模型或复杂迁移才走完整数据模型契约。若新增字段改变业务身份、归属、唯一性、状态机或删除语义，自动升级为完整契约。新增持久化表仍必须取得用户对列明表名的明确同意；模型批准不等于数据库执行授权。

## 风险、文档与 Git

- 权限扩大、资金计算、数据迁移、不可逆写库、生产发布、提交/推送/合并等动作仍需当前任务的明确授权；“按闭环做”不等于自动获得这些权限。
- 只更新本次行为实际影响的文档：项目已有的 PRD/ADR/研究记录、接口或数据库说明、项目 `AGENTS.md` 中已有的专属区块。不要为每个任务新建 brief、handoff 或控制台账，也不要修改 Magpie 的全局资源库。
- 改动后检查 `git status` 和实际 diff，区分产品代码、测试、文档和用户已有改动。提交、推送和创建 PR 只在用户明确要求时进行，并遵循项目的 Git 约定。
- 不把编译通过、MCP 已连接、Skill 已存在或测试文件已创建当作业务验收。按“验收项 → 实际证据 → 未验证边界”报告。

## 验收门槛

1. **源码/逻辑**：用户明确要求测试、验收或运行验证时，相关测试、静态检查、类型检查或构建按项目真实命令执行；普通实现未获测试授权时只核对改动和差异，不自动运行测试，交付时说明未验证边界。
2. **接口/数据**：接口契约、权限、数据库结构和迁移必须有可复现证据；数据库写入和迁移按授权执行。
3. **回归**：用户要求回归证明时，建立能区分修复前后的证据；未要求时不强制编写或运行回归测试。
4. **文档**：只有受影响的文档需要同步，内容必须和实际行为、字段、接口或决策一致。

## 交付输出

复杂任务在开始时用一行说明内部路由，例如“路由：需求澄清 → 实现 → 按授权验证”；简单任务直接做，不展示流程仪式。最终只报告：

- 完成的用户可见结果和关键改动；
- 实际执行的验证及结果；
- 未验证的边界、阻塞和仍需的授权；
- 受影响文档或 Git 状态（仅在实际发生或需要用户决定时）。

阶段文档中的自动测试、自动 Issue 创建、自动 commit、自动 review 等默认动作，只有在项目已配置且当前请求明确授权时才执行；否则作为建议或可选的下一步，不阻塞当前范围内的实现。



## 上游保真与调度边界

- 保留作者方法，但为当前插件移除未安装技能的调用和不可达引用；已获本地适配的 implement、review 及必要兼容修改以实际安装版本为准。answer-me-with-html 不改写。
- 上游阶段是可选方法，不是必须整段执行的流水线。当前任务授权决定可执行范围，技能描述、完成门槛及模板不扩大授权。
- 明确需求可使用本地适配的 implement，由主代理直接实现；不自动测试、委派或提交。小改仍直接完成。
- review 默认主代理聚焦审查，三个检查视角不等于三个代理；明确授权独立审查或委派后才按需选择审查者，不固定人数。
- debug 的复现、测试和仪器化步骤按授权取用。没有运行授权时只做静态分析及已授权修复，不声称满足上游运行证明门槛。
- setup-project 仅在明确初始化需求时选择；普通任务不因缺少 docs/agents 或 tracker 而初始化。入口协议仅取当前任务需要的上下文，不把可选阶段的配置要求扩展成所有任务的前置条件。
- 上游引用未选装技能、模板示例或参考路径时，先判断是否任务必需；不加载不存在的文件，不自动补装，也不改写上游来隐藏缺失。确实依赖时说明能力边界。

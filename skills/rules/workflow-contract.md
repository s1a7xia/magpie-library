# Workflow Contract

本文件是阶段入口、产物、退出门和失败回流的单一契约。各技能只在正文中写自己的方法；阶段边界以此处为准。项目 AGENTS.md 负责启用工作流、授权、编译口径、提交和页面验收时机；本契约不把项目策略施加到无关项目。小改可走 Direct，不强制完整阶段链。

## 1. 选择路径

| 路径 | 适用 | 入口 | 不做什么 |
|---|---|---|---|
| **Direct** | 错字、样式微调、单文件小修、明确低风险改动 | 主代理直接处理 | 不建 PRD，不进入 `implement`，不把验收说成完成 |
| **Slice** | 已有冻结基线，只推进已批准切片 | `implement` | 不重新拆需求，不自动补业务范围 |
| **Baseline** | 新需求、多方案、跨模块、验收口径不清 | `think` → `grill` → `story` → `implement` | 不跳过基线直接写代码 |

项目可通过 AGENTS.md 批准端到端续接；该批准不越过业务基线确认或外部写入授权。`review` 与 `page-acceptance` 不属于自动续接范围，始终由用户单独明确发起；“端到端完成”不能自动启动这两个阶段。未配置续接时，产品阶段 `setup-project`、`think`、`grill`、`story`、`implement`、`page-acceptance`、`review` 需要用户明确发起。`debug` 可在出现报错、崩溃或回归时自动进入，也可由 `page-acceptance` / `review` 在确认范围内缺陷时内部调用。未获续接授权时，阶段结束停止并提示下一步；已获续接授权时仅续接明确允许的阶段，遇基线确认、权限边界或手动门仍停止。

## 2. 阶段契约

| 阶段 | 进入条件 | 必须产出 | 完成后的下一步 | 不满足时 |
|---|---|---|---|---|
| `setup-project` | 新项目、重配或项目事实漂移 | `docs/agents/` 项目事实、profile、编译/启动命令 | `/think`、`/research`，或已有切片时 `/implement` | 报告待确认事实；不猜端口、命令或仓库关系 |
| `think` | 需求确实未收敛，或多个方案实质不同 | 获批设计摘要；或 `Status: Draft` 的 PRD | `/grill`（仅 PRD 路径） | 用户拒绝 PRD 时停在设计摘要，不进入 grill/story |
| `grill` | 已有获批 PRD，且用户明确发起 | `Status: Grilled`、术语、必要 ADR、Change Log | `/story` | 目标或范围实质变化时退回 `/think`；事实缺失时自查 |
| `story` | PRD 为 `Grilled` 且一致性门通过 | `Sliced into`、依赖、`Covers`、`Status: Sliced` | `/implement` | 基线不自洽时回 `grill`；不改写需求 |
| `implement` | 已批准切片 | 完整代码、覆盖映射；检查与 Git 独立记账，Dev Complete | 用户手动 `/review` | 无基线报告上游缺口 |
| `page-acceptance` | 用户单独明确发起、环境可用；默认 review 后 | 完整范围验收、证据；有效 review 齐备则 Done | 收尾或手动针对性 review | 环境不可用/三轮失败报告阻塞 |
| `review` | 用户单独明确发起；不要求已有页面验收 | 审查、debug 修复并继续本轮、最终代码证据 | UI：用户手动 `/page-acceptance`；非 UI 可 Done | 未通过保持实际状态 |
| `debug` | 出现报错、崩溃、回归或已确认缺陷 | 根因证据、修复；授权时复测，否则记录静态核对与运行缺口 | 返回调用阶段；独立修复按第 4 节交接 | 缺必要证据或三轮假设失败时输出交接；静态诊断可继续，不冒充复现 |

## 3. 产物与状态

- **PRD**：`docs/prd/PRD-NNNN-<title>.md` 是需求、验收标准和切片状态源。`Status` 与 `Sliced into` 优先于口头描述。
- **项目事实**：`docs/agents/coding-standards.md` 记录 profile、约定和真实命令；`project-state.md` 记录当前目标、阶段、阻塞、下一步和运行命令。
- **验证证据**：`docs/agents/verification.md` 记录代码版本、路径/命令、结果、日期和来源（agent/user）。数据库脚本另区分“已编写 / 未执行 / 执行成功 / 失败或部分执行”；获授权执行后记录环境、库/schema/数据库版本、脚本路径及版本或摘要、执行时间、影响范围/行数、实际结果与回退/恢复状态。未知项如实说明；Git 提交不证明目标库已迁移。不写凭证、认证头或隐私数据。
- **阶段状态**：字段与状态转换的唯一详细定义见 [PRD 生命周期](../think/PRD-FORMAT.md#prd-生命周期状态)；本契约只定义阶段边界、授权和证据回流，不另设状态定义。
- **代码事实**：当前 checkout、当前项目实现和适用规范优先于历史总结、聊天记忆和外部示例。

冻结后的新增或变更先写 PRD `Change Log`。目标和范围不变时，回到 `Grilled`，由 `story` 为变更的 `R#` / `AC#` 补切片，受影响切片在变更实现前为 `In Progress`，只作废受影响 review/验收证据；目标和范围实质变化时回到 `Draft`。

## 4. 验收门槛与回流

验收门槛按**可观察影响**判断，不按文件位置判断：

- **有页面可观察影响**：默认顺序：开发完成 → 用户手动 review（确认缺陷当场 debug，修复后继续本轮审查并覆盖最终代码）→ 用户手动 page-acceptance（完整声明页面范围）→ Done。review 不以前置页面验收为门槛，也不自动启动页面验收。无页面影响记 N/A，review 通过且收尾完成即可 Done。已有有效页面验收可复用，仅复验受影响范围。验收内确认缺陷当场 debug 并局部复验；涉及权限、事务、数据模型或复杂状态的实质修复使相关 review 证据失效，提示用户手动发起针对性 review；普通样式/反馈修正不要求重跑整轮 review。没有覆盖声明范围的首次验收，不能仅用修复点验证宣称整批通过。
- **无页面可观察影响**：经调用链和消费者核对，确实不改变页面展示、交互、数据或权限结果的后端内部逻辑、后台任务、日志等改动。SQL、配置、接口或任务不是天然免验收：菜单、字典、角色授权、路由、页面消费的业务数据或参数变化仍可能有页面影响，应记录待用户手动验收的相关路径，不自动打开浏览器。确认无影响才记 `Page acceptance: N/A — <reason>`；无法判断时记待确认，不凭文件扩展名判 N/A。`review` 仍可基于现有证据和代码执行，不自动构建。
- **混合范围**：分别判断。UI 范围遵守页面验收门槛；非 UI 范围不因缺少浏览器证据被误判为阻塞，但也不能拿非 UI 证据证明页面可用。

| 情况 | 处理 |
|---|---|
| 基线被用户拒绝 | 停在设计摘要；只有任务本身符合 Direct 条件时才可直接处理 |
| 冻结后发现新需求 | 写 `Change Log`；按目标和范围变化程度回到 `Grilled` 或 `Draft` |
| `implement` 发现基线未决 | 停止受影响切片并报告上游需处理；不自动调用 `grill` |
| `implement` 发现非阻塞业务口径 | 按推荐默认完整实现，记录 `TODO(待确认)`；不用 TODO 代替接口、页面、数据或校验 |
| 不可逆数据、权限扩大或安全风险无安全默认 | 停止受影响动作或切片并报告 |
| 技术实现未知且本地能力未覆盖 | 停止受影响切片并报告 `Next: /research`；冻结基线后不从 `implement` 发起调研 |
| 页面验收或 review 发现确认缺陷 | 当前阶段内进入 `debug`；修复后只按授权核对受影响路径。review 必须继续本轮剩余检查并覆盖修复后的代码，不提前结束或等待用户重新启动 review；只读请求只报告 |
| `review` 修复改变页面可观察行为 | 受影响范围退回 `Dev Complete`；整轮 review 后提示手动验收：无有效首次验收则覆盖完整声明范围，有则仅复验受影响路径 |
| `review` 修复不改变页面可观察行为 | 保留原验收证据，记录覆盖边界，继续完成本轮 review |
| 构建或明确要求的检查失败 | 不宣称验证通过；若暴露代码缺陷则实现未完成，否则分别记录实现状态和环境/验证阻塞 |

## 5. 检查授权与完成口径

默认只阅读相关代码、核对 diff 和字段/调用关系，不写或运行测试、lint、类型检查、构建或浏览器验证。仅当前请求明确授权或更高优先级指令明确要求时执行最小范围；项目命令表、profile 和技能建议不构成授权。显式页面验收授权声明范围内的浏览器检查，不授权建测试框架、构建/部署或任意写库；数据边界另行确认。

| 维度 | 记录什么 |
|---|---|
| Implementation | 每条验收标准对应的实现；未实现/有代码缺陷时保持 In Progress |
| Verification | 实际 pass / fail / not run / blocked、版本、范围及来源；未运行不等于实现缺失，也不等于验证通过 |
| Git | 未授权 / 未提交 / 已提交 / 已推送 / 阻塞及原因；非 Git 目录不阻塞本地实现 |
| Closure | 正式 PRD 的 Done 仍需有效手动 review、页面验收或 N/A，以及项目实际启用的收尾/发布门；无授权不能用“略过检查”伪造通过 |

构建通过不证明页面可用；静态代码审查不证明运行行为。复用覆盖最终代码的已有证据，相关输入未改变不重复执行检查。Direct 任务完成不强制套用正式 PRD 的 Done 门。

## 6. 工作区自检与自动收尾

本节的“自动”指 Agent 在阶段开始和结束主动检查并处理，不依赖用户查看 IDE 的 Git 面板，也不等于工程 Hook。Hook 仍按 [hook-guardrails.md](hook-guardrails.md) 作为可选护栏。

### 6.1 阶段开始：记录工作区基线

凡可能写入文件的任务，在第一次修改前于实际仓库根目录记录（非 Git 目录只记录相关文件的改前内容/备份，不创建仓库）：

- 当前分支、`HEAD` 和上游（如有）；
- `git status --short -uall`；
- 已暂存路径（`git diff --cached --name-status`）；
- 未暂存路径（`git diff --stat`）；
- 未跟踪文件（`git ls-files --others --exclude-standard`）。

把结果作为本次任务的**保护基线**保存在当前上下文。基线中的改动属于用户或其它会话，不得 stash、reset、clean、覆盖、代为提交或算作本轮产物。先以实际 Git 根目录确认仓库边界，子目录不等于独立仓库。多仓库任务才按 `docs/agents/repo-map.md` 对每个实际参与仓库分别记录分支、提交及推送结果，并明确唯一需求/状态事实源和协同发布顺序；单仓不新增分仓流程。只读任务在输出中声明“未写入工作区”，不要求 commit。

### 6.2 阶段结束：自动核对并收尾

每次收尾时只核对参与目录的实际差异、暂存区和状态，与保护基线比较；无需反复输出全仓清单。非 Git 目录按具体文件记录改前/改后，不创建仓库。分类：

| 分类 | 处理 |
|---|---|
| 本轮代码、文档或配置 | 按用户或项目既有授权核对 diff 后精确暂存并提交；已授权推送且有明确可写上游时推送，再核验本地 `HEAD`、`@{u}` 和远端 |
| 本轮明确生成的临时日志、备份、调试文件 | 自动清理；属于验收证据或用户资料的例外应保留并说明 |
| 阶段开始前已存在的改动 | 保留原状，只报告；绝不自动清理、回滚或扫入本轮提交 |
| 归属不明或无法安全分离的改动 | 停止本轮提交，报告路径和需要用户确认的事项 |

提交前记录已有暂存区；没有既有暂存时只暂存实际属于本轮的路径。禁止用 `git add -A` 代替归属核对。用户明确要求“先别提交”时保留本轮改动，并说明未提交清单。

### 6.3 文档 freshness 门

提交前检查本次工作是否使项目事实失真，至少覆盖：

| 变化 | 必须核对 |
|---|---|
| 需求、验收标准、切片或变更记录 | PRD 的 `Status`、`Sliced into`、`Change Log` 等实际章节 |
| 当前阶段、阻塞、下一步或运行方式 | `docs/agents/project-state.md` |
| 编译、页面验收、review 或未验证项 | `docs/agents/verification.md` |
| 持久架构/业务取舍 | ADR 或 `docs/agents/project-decisions.md` |
| 可复用技术调研 | `docs/research/` 记录及 `INDEX.md` |
| 领域术语 | `CONTEXT.md` |
| 项目配置、profile、命令、端口或仓库关系 | `domain.md`、`coding-standards.md` 或 `repo-map.md` |

必须实际读取并更新适用的状态行或证据，不能只假定“另一个阶段会补”。没有适用文档变化时，在交付中写明 `Docs: no change — <reason>`。文档缺失且任务不足以安全创建时，报告缺口，不擅自补模板。

### 6.4 工作区收尾

阶段结束时核对真实工作区状态，但不在最终回复中输出固定格式的工作区回执。实现、检查、文档和 Git 分别报告。未授权提交、非 Git 目录或推送阻塞不否定已完成的本地实现；已授权而未完成的 Git 收尾需明确列出，不宣称已提交/已推送或满足正式收尾门。文档 freshness 未核对不能宣称状态已同步。提交后至少再次确认没有本轮未暂存或未跟踪残留，并区分仍然存在的基线脏改动。推送后核验本地 HEAD、上游和远端，但不要求附加固定格式的推送回执。

### 6.5 停止边界

- 单分支开发；不自动创建功能分支、PR、合并或部署。
- 提交/推送已获授权时，按切片在当前分支精确提交，推送到已确认可写上游；未授权则保留改动并报告，不反复询问。提交信息带切片说明。
- 旧暂存或混杂改动无法安全保留并分离、冲突/变基、敏感信息、无提交身份、受保护或默认分支、非 Git 目录或上游不明确时停止对应 Git 动作并说明；不阻塞可安全完成的实现，不强推、不绕过钩子、不改写历史。
- 未获阶段续接授权、遇手动门或需要用户决策时停止；阻塞只停受影响动作。仅报告必要结果、证据、限制和下一步，不自行扩大范围。

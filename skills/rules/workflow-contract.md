# Workflow Contract

本文件是阶段入口、产物、退出门和失败回流的单一契约。各技能只在正文中写自己的方法；阶段边界以此处为准。全局指令负责授权、编译口径、提交和页面验收时机。

## 1. 选择路径

| 路径 | 适用 | 入口 | 不做什么 |
|---|---|---|---|
| **Direct** | 错字、样式微调、单文件小修、明确低风险改动 | 主代理直接处理 | 不建 PRD，不进入 `implement`，不把验收说成完成 |
| **Slice** | 已有冻结基线，只推进已批准切片 | `implement` | 不重新拆需求，不自动补业务范围 |
| **Baseline** | 新需求、多方案、跨模块、验收口径不清 | `think` → `grill` → `story` → `implement` | 不跳过基线直接写代码 |

产品阶段 `setup-project`、`think`、`grill`、`story`、`implement`、`page-acceptance`、`review` 需要用户明确发起。`debug` 可在出现报错、崩溃或回归时自动进入，也可由 `page-acceptance` / `review` 在确认范围内缺陷时内部调用。阶段结束必须停止，并提示下一步；不得自动加载或执行下一产品阶段。

## 2. 阶段契约

| 阶段 | 进入条件 | 必须产出 | 完成后的下一步 | 不满足时 |
|---|---|---|---|---|
| `setup-project` | 新项目、重配或项目事实漂移 | `docs/agents/` 项目事实、profile、编译/启动命令 | `/think`、`/research`，或已有切片时 `/implement` | 报告待确认事实；不猜端口、命令或仓库关系 |
| `think` | 需求确实未收敛，或多个方案实质不同 | 获批设计摘要；或 `Status: Draft` 的 PRD | `/grill`（仅 PRD 路径） | 用户拒绝 PRD 时停在设计摘要，不进入 grill/story |
| `grill` | 已有获批 PRD，且用户明确发起 | `Status: Grilled`、术语、必要 ADR、Change Log | `/story` | 目标或范围实质变化时退回 `/think`；事实缺失时自查 |
| `story` | PRD 为 `Grilled` 且一致性门通过 | `Sliced into`、依赖、`Covers`、`Status: Sliced` | `/implement` | 基线不自洽时回 `grill`；不改写需求 |
| `implement` | 已有批准切片，覆盖门通过 | 代码、受影响侧编译、逐片提交/推送、`Dev Complete` | 有 UI 可观察变化：`/page-acceptance`；否则 `/review` | 无切片回 `story`；基线未决回上游；阻塞切片保持 `In Progress` |
| `page-acceptance` | 用户明确发起，目标环境可用 | `Accepted`；review 后的修复点通过时写 `Done` | `/review`（首次验收）；或收尾 | 环境不可达记 `blocked`；三轮修复仍未通过则停止并报告 |
| `review` | 用户明确发起；UI 可观察范围已有有效验收，或该范围记 `N/A` | 审查报告、必要修复、状态写回；非 UI 批次可从 `Dev Complete` 直接写 `Done` | 行为变化修复：`/page-acceptance`；否则 `Done` | 证据不足或基线未决时停止；不能用修复点验收替代首次验收 |
| `debug` | 出现报错、崩溃、回归或已确认缺陷 | 根因、修复、受影响路径复测 | 返回调用阶段；独立修复按第 4 节交接 | 无法复现或三轮假设失败时输出阻塞证据 |

## 3. 产物与状态

- **PRD**：`docs/prd/PRD-NNNN-<title>.md` 是需求、验收标准和切片状态源。`Status` 与 `Sliced into` 优先于口头描述。
- **项目事实**：`docs/agents/coding-standards.md` 记录 profile、约定和真实命令；`project-state.md` 记录当前目标、阶段、阻塞、下一步和运行命令。
- **验证证据**：`docs/agents/verification.md` 记录代码版本、路径/命令、结果、日期和来源（agent/user）。不写凭证、认证头或隐私数据。
- **阶段状态**：`think` 写 `Draft`；`grill` 写 `Grilled`；`story` 写 `Sliced`；`implement` 写 `In Progress` / `Dev Complete`；`page-acceptance` 为 UI 范围写 `Accepted`，或在 review 已覆盖最终代码后写 `Done`；`review` 在无需修复点验收时写 `Done`，非 UI 批次可凭编译和审查证据从 `Dev Complete` 直接写 `Done`。
- **代码事实**：当前 checkout、当前项目实现和适用规范优先于历史总结、聊天记忆和外部示例。

冻结后的新增或变更先写 PRD `Change Log`。目标和范围不变时，回到 `Grilled`，由 `story` 为变更的 `R#` / `AC#` 补切片，受影响切片退回 `Dev Complete` 并作废旧验收；目标和范围实质变化时回到 `Draft`。

## 4. 验收门槛与回流

验收门槛按**可观察影响**判断，不按文件位置判断：

- **有页面可观察影响**：会改变渲染页面、交互、显示数据、权限表现或视觉结果。必须在 `review` 前完成首次全范围 `page-acceptance`；review 后若修复改变这些行为，只对修复点及连带路径再做一次窄验收。
- **无页面可观察影响**：纯后端内部逻辑、后台任务、SQL 迁移、日志、配置或不经过页面的契约改动。`review` 可基于受影响侧编译和现有证据执行，并明确记录 `Page acceptance: N/A — <reason>`。
- **混合范围**：分别判断。UI 范围遵守页面验收门槛；非 UI 范围不因缺少浏览器证据被误判为阻塞，但也不能拿非 UI 证据证明页面可用。

| 情况 | 处理 |
|---|---|
| 基线被用户拒绝 | 停在设计摘要；只有任务本身符合 Direct 条件时才可直接处理 |
| 冻结后发现新需求 | 写 `Change Log`；按目标和范围变化程度回到 `Grilled` 或 `Draft` |
| `implement` 发现基线未决 | 停止受影响切片并报告上游需处理；不自动调用 `grill` |
| `implement` 发现非阻塞业务口径 | 按推荐默认完整实现，记录 `TODO(待确认)`；不用 TODO 代替接口、页面、数据或校验 |
| 不可逆数据、权限扩大或安全风险无安全默认 | 停止受影响动作或切片并报告 |
| 技术实现未知且本地能力未覆盖 | 仅在 `implement` 做一次有界联网调研，回到当前切片 |
| 页面验收或 review 发现确认缺陷 | 当前阶段内进入 `debug`；修复后只重测受影响路径 |
| `review` 修复改变页面可观察行为 | 受影响范围退回 `Dev Complete`；整轮 review 后做一次修复点验收 |
| `review` 修复不改变页面可观察行为 | 保留原验收证据，记录覆盖边界，继续完成本轮 review |
| 构建或明确要求的检查失败 | 不宣称完成；记录实际失败和未验证项 |

## 5. 检查矩阵

| 改动类型 | 默认检查 | 页面验收 |
|---|---|---|
| 纯文档 | 核对 diff 和相对链接 | 不需要 |
| 后端 / SQL / 内部逻辑 | 编译受影响后端；review 相关调用和风险 | 无页面可观察影响时 `N/A` |
| React 页面 / API 契约影响页面 | 构建受影响前端；review 契约和调用链 | 首次全范围页面验收 |
| 跨前后端业务闭环 | 编译/构建受影响侧；核对字段、路径、权限和状态 | 首次全范围页面验收 |
| 明确要求的测试 | 只运行要求的最小目标 | 测试不能替代页面验收 |

默认不编写、修改或运行测试；用户明确要求时才执行。编译通过不等于页面可用，代码审查也不能替代渲染验证。视觉结论以真实渲染和截图为准。

## 6. 工作区自检与自动收尾

本节的“自动”指 Agent 在阶段开始和结束主动检查并处理，不依赖用户查看 IDE 的 Git 面板，也不等于工程 Hook。Hook 仍按 [hook-guardrails.md](hook-guardrails.md) 作为可选护栏。

### 6.1 阶段开始：记录工作区基线

凡可能写入文件的任务，在第一次修改前于实际仓库根目录记录：

- 当前分支、`HEAD` 和上游（如有）；
- `git status --short -uall`；
- 已暂存路径（`git diff --cached --name-status`）；
- 未暂存路径（`git diff --stat`）；
- 未跟踪文件（`git ls-files --others --exclude-standard`）。

把结果作为本次任务的**保护基线**保存在当前上下文。基线中的改动属于用户或其它会话，不得 stash、reset、clean、覆盖、代为提交或算作本轮产物。多仓库任务按 `docs/agents/repo-map.md` 对每个实际参与的仓库分别记录。只读任务在输出中声明“未写入工作区”，不要求 commit。

### 6.2 阶段结束：自动核对并收尾

每次独立任务、切片交付、批次收口或显式阶段结束前，重新执行上述命令，并与基线比较并分类：

| 分类 | 处理 |
|---|---|
| 本轮代码、文档或配置 | 核对 diff 后精确暂存并提交；有明确可写上游时推送，再核验本地 `HEAD`、`@{u}` 和远端 |
| 本轮明确生成的临时日志、备份、调试文件 | 自动清理；属于验收证据或用户资料的例外应保留并说明 |
| 阶段开始前已存在的改动 | 保留原状，只报告；绝不自动清理、回滚或扫入本轮提交 |
| 归属不明或无法安全分离的改动 | 停止本轮提交，报告路径和需要用户确认的事项 |

提交前记录已有暂存区；没有既有暂存时只暂存实际属于本轮的路径。禁止用 `git add -A` 代替归属核对。用户明确要求“先别提交”时保留本轮改动，并说明未提交清单。

### 6.3 文档 freshness 门

提交前检查本次工作是否使项目事实失真，至少覆盖：

| 变化 | 必须核对 |
|---|---|
| 需求、验收标准、切片或变更记录 | PRD 的 `Status`、`Sliced into`、`Change Log` 等实际章节 |
| 当前阶段、阻塞、下一步或运行方式 | `docs/agents/project-state.md` |
| 编译、页面验收、review 或未验证项 | `docs/agents/verification.md` |
| 持久架构/业务取舍 | ADR 或 `docs/agents/project-decisions.md` |
| 可复用技术调研 | `docs/research/` 记录及 `INDEX.md` |
| 领域术语 | `CONTEXT.md` |
| 项目配置、profile、命令、端口或仓库关系 | `domain.md`、`coding-standards.md` 或 `repo-map.md` |

必须实际读取并更新适用的状态行或证据，不能只假定“另一个阶段会补”。没有适用文档变化时，在交付中写明 `Docs: no change — <reason>`。文档缺失且任务不足以安全创建时，报告缺口，不擅自补模板。

### 6.4 工作区收尾

阶段结束时核对真实工作区状态，但不在最终回复中输出固定格式的工作区回执。本轮应有的代码或文档仍未提交、文档 freshness 未核对、提交后仍有本轮残留，或工作区无法安全分离时，不得宣称任务完成；只在存在未提交改动或阻塞时说明具体路径和原因。提交后至少再次确认没有本轮未暂存或未跟踪残留，并区分仍然存在的基线脏改动。推送后核验本地 HEAD、上游和远端，但不要求附加固定格式的推送回执。

### 6.5 停止边界

- 单分支开发；不自动创建功能分支、PR、合并或部署。
- 按切片推进时，每片在当前分支提交并推送一次，提交信息带切片说明。
- 无关暂存、混杂改动无法可靠分离、冲突/变基、敏感信息、无提交身份、受保护或默认分支、非 Git 目录或上游不明确时停止并说明；不强推、不绕过钩子、不改写历史。
- 阶段完成、阻塞或需要用户决策时立即停止；只报告必要结果、证据、限制和下一步，不自行扩大范围。

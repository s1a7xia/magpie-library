# 通用工程工作流

从当前任务进入需要的阶段，复用已有技能，不要求每次走完整流水线。项目规则、用户当次要求与实际工具能力决定执行范围；固定目录、框架、测试命令、模型和供应商不写在本技能中。

## 任务路径

先按任务规模选路径，不把完整流程套在单点改动上；判断不准时取更高一级。

| 路径 | 适用 | 执行方式 | 文档与提交 |
|---|---|---|---|
| **Direct** | 单点、明确、低风险：错字、样式微调、单文件小修 | 主代理直接实现并核对 diff | 不建 PRD；按通用提交规则处理 |
| **Slice** | 已有冻结基线，只推进一个或少量已拆切片 | `implement` | PRD 切片状态；逐片提交 |
| **Baseline** | 新需求、多方案、跨模块、验收口径不清 | `think` → `grill` → `story` → `implement` | PRD、必要 ADR、基线页、切片 |

新功能默认走 **Baseline**；纯排障走 `debug`，不为了套流程先补一套 PRD。只有实际需要并行、追踪或批次交付时才拆切片。

## 进入当前项目

- 多 Agent 协作或项目启用了微信入口时，先读 `docs/agents/ai-collaboration.md` 并按 [ai-collaboration](../ai-collaboration/SKILL.md) 执行；单 Agent 会话不加载该技能。微信入口只读取项目状态供手机查看，不开发、不测试、不改最终状态。
- 从用户指定目录或当前工作目录识别工程；在 Git 工程中核对仓库根、分支、工作区和暂存区，记录本任务改动范围。多仓库时分别记录。
- 读取适用的 AGENTS.md 及任务所需的配置、代码与文档入口。只取相关上下文，不全库扫描。项目未配置技能文档入口时从实际目录发现，不强制创建一套模板。
- `docs/agents/project-state.md`、`project-decisions.md`、`verification.md` 存在时，读取当前任务相关部分：状态用于续接，决策用于避免反复推翻已确认选择，验证记录只作为版本相关的证据线索。没有这些文件时按现有项目事实推进，不擅自创建。
- 从现有清单、构建文件、启动说明和项目规则取得命令、文档位置、技术栈及特殊限制；缺少关键业务决策时才询问。
- 切换项目时核对实际浏览器 URL、数据库/SSH 目标，不假设资源库连接会随工作目录切换。并发改动先区分归属，不覆盖其他会话的更新。

## 按任务选阶段

| 情形 | 处理 |
|---|---|
| 新项目初始化、或需要重配项目协作/技术配置 | **显式**使用 `setup-project`；它是项目配置入口，不是每个开发任务的前置门槛 |
| 需求真正模糊，或存在多个实质不同的方案 | **显式**使用 `think`。`think` 完成后**自动进入** `grill`；也可手动直接触发 `grill` |
| 技术版本、框架行为、官方最佳实践影响方案 | 使用 `research`：可显式独立发起，也可由 `think`/`implement`/`debug` **隐式触发**。必须联网取权威来源 |
| 已有冻结基线，需要拆成可执行切片 | 使用 `story`。前置条件：PRD 的 `Status` 必须是 `Grilled`；没有基线先走 `think`→`grill` |
| 按已拆切片集中开发 | **显式**调用 `implement`。一次推进一批切片，批次结束后停下等确认 |
| 单个切片写完 | 主代理自检：编译受影响的一侧 + 核对 diff。**不做页面测试**，然后提交并推送该切片 |
| 整批切片开发完成 | 提示可以开始页面测试；**由用户主动发起** `page-acceptance`，不自动执行 |
| 页面测试或 review 发现缺陷 | **自动**进入 `debug`，修完只重测受影响切片；验证→修复→重测最多三轮 |
| 页面测试通过后需要完整把关 | **仅用户明确调用** `review` 技能时执行三视角审查。确认缺陷自动 `debug`；设计/风格/可维护性建议只列出 |
| 计划外的突发故障（报错、崩溃、回归） | **自动**使用 `debug`；若该缺陷属于已冻结基线，回到 `implement` 对应切片处理 |
| 需要建 Issue、开 PR/MR、同步远端任务状态 | 使用 `scm-collaboration`。本地提交推送不触发它 |
| 写前端视图文件（.vue/.tsx/.css/.scss/组件/布局） | **自动**加载 `frontend-design`；只改数据层或纯后端时不加载 |
| 修改业务代码、plus-ui、SQL | 按当前用户指令和项目 `coding-standards.md` / `AGENTS.md` 选择技术档案；项目未配置时使用全局 `ruoyi-plus-dev` 默认，显式 `none` 或其他 profile 覆盖默认 |
| 需要把结论可视化 | 基线冻结时**自动**用 `answer-me-with-html` 出基线页；切片多或依赖复杂时在 story 后出页 |
| 复杂、跨步骤、高风险或需求草稿化 | 主代理按 `prompt-engineering` 执行模式内部整理后直接执行；不展示提示词稿、不等待确认 |
| 简单、明确且低风险的实现指令 | 直接执行，不套提示词流程 |
技能不可用时说明并用能完成任务的现有能力处理，不假称调用。不要因 review/implement 的宽泛描述自动启动重流程。

技能正文可能提到未随当前资源库安装的可选技能（例如架构审查或写作技能）。这些名称不是隐式依赖：只有实际安装并通过入口确认可用时才读取；缺失时用当前技能的直接实现/审查步骤完成，并记录未覆盖的能力，不阻塞主任务。

## 两道质量门

1. **拆片前：基线一致性门。** `story` 在切片前核对 PRD 已冻结、无未决项、每条需求至少有一条可观察的验收标准、术语与范围不冲突。不通过就回 `grill`；不拿自相矛盾的基线拆任务。
2. **收口时：规格覆盖门。** `implement` 在批次收口核对每条需求与验收标准都有切片承接且达到 `Dev Complete`。覆盖不全时不得把 PRD 标为 `Dev Complete`；缺切片回 `story`，实现缺口留在原切片修。

这两道门检查的是“需求是否完整落到实现”，不是重复页面测试。运行时是否可用仍由用户发起的 `page-acceptance` 判定。

## 执行口径

切片自检、编译范围、页面测试时机、提交与推送粒度、失败处理，全部以全局协作指令和项目 `AGENTS.md` 为准，本技能不复述。这里只保留路由判断：当前情形该进入哪个技能。

按切片推进时的顺序是固定的：`implement` 逐片实现并提交推送 → 整批结束后由用户发起 `page-acceptance` → 缺陷自动进 `debug` 并只重测受影响切片 → 用户明确调用 `review` 后才做完整审查。细节见各技能正文，不在本表重复。

项目配置了 `docs/agents/project-state.md` 时，只在阶段转换时更新其中“当前批次”的阶段面板：基线冻结、切片完成、批次收口、页面验收、review 收口。PRD 的 `Status` 与 `Sliced into` 仍是需求状态源，面板只做总览，不复制需求内容。

## 资源库自检与维护

资源库是跨项目复用的源；Codex 的 `AGENTS.md` 和技能副本是生成结果。修改资源库后先运行：

```powershell
magpie library sync
python C:\Users\s1a71\.config\magpie\library\skills\engineering-workflow\scripts\verify-library.py
```

健康检查验证技能清单、frontmatter、相对链接、同步和哈希，并对 MCP 头中的内联凭证给出提示；不验证 MCP 连通性、模型供应商、插件运行状态或项目业务测试。发现技能副本或指令不一致时先修复源配置并重新同步，不要直接改生成副本掩盖问题。MCP 报传输错误时先核对 Magpie 端口和当前 Codex 会话，不能把“服务在监听”当成“本会话已连通”。插件和模型组属于 Magpie 运行配置，不由本技能假装管理。

## 工具分工

MCP 是工具而非自动任务：浏览器用于界面；文档工具用于版本依据；数据库/SSH 先核对目标环境与操作范围。已有连接不代表授权写入，不主动巡检所有服务。

工具不可用、超时或报错时依据实际错误采取有界处理，不无变化重试或伪造成功；替代方式须保持原有授权边界。缺失必要工具需安装、联网付费或扩大权限时，先报告具体条件。部署/数据库写入按明确授权、影响范围与必要回退条件执行，复用已有方案，不另外强建发布框架。

RTK 保留终端输出压缩。各 Agent 的模型与工具选择沿用现有配置，本技能不重写路由。

需要完整使用说明或换项目示例时，读取 [使用指南](references/usage.md)。

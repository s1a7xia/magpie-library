# 通用工程工作流

从当前任务进入需要的阶段，复用已有技能，不要求每次走完整流水线。项目规则、用户当次要求与实际工具能力决定执行范围；固定目录、框架、测试命令、模型和供应商不写在本技能中。

## 进入当前项目

- Codex/dsh 协作时，先读项目 `docs/agents/ai-collaboration.md` 和相关任务记录；当前角色按 [ai-collaboration](../ai-collaboration/SKILL.md) 执行。Codex 负责其开发任务的验证与交付；普通 dsh 项目按用户需求正常工作。微信工作区默认日常聊天，仅动作前缀触发项目动作；微信助手负责需求目录、调研简报与简短状态答复，不执行测试或交付。
- 从用户指定目录或当前工作目录识别工程；在 Git 工程中核对仓库根、分支、工作区和暂存区，记录本任务改动范围。多仓库时分别记录。
- 读取适用的 AGENTS.md 及任务所需的配置、代码与文档入口。只取相关上下文，不全库扫描。项目未配置技能文档入口时从实际目录发现，不强制创建一套模板。
- `docs/agents/project-state.md`、`project-decisions.md`、`verification.md` 存在时，读取当前任务相关部分：状态用于续接，决策用于避免反复推翻已确认选择，验证记录只作为版本相关的证据线索。没有这些文件时按现有项目事实推进，不擅自创建。
- 从现有清单、构建文件、启动说明和项目规则取得命令、文档位置、技术栈及特殊限制；缺少关键业务决策时才询问。
- 切换项目时核对实际浏览器 URL、数据库/SSH 目标，不假设资源库连接会随工作目录切换。并发改动先区分归属，不覆盖其他会话的更新。

## 按任务选阶段

| 情形 | 处理 |
|---|---|
| 新项目或项目结构/技术栈/协作方式变化 | 用户要求初始化或重配时使用 `setup-project`；普通小任务不强制先做项目模板 |
| 清楚的小需求、局部修复 | 直接实现或使用 debug，不创建无用 PRD |
| 技术版本、框架行为、官方最佳实践影响方案 | 按需使用 `research` 核对权威来源；已安装 Context7 时优先查官方文档，不用未核实记忆替代。多来源或跨版本调研由主代理直接取证、核验来源并写记录 |
| 复杂需求、需要做方案选择 | 按需 think；重要方案用 grill；已确认的大任务用 story 拆分 |
| GitHub/GitLab/Gitee/本地任务单协作 | 按需使用 `scm-collaboration`；先识别实际远程与 tracker，连接不等于写入授权。GitHub 与 Gitee 走 Magpie MCP，GitLab 走 `glab` CLI |
| 按既定计划集中开发 | 用户明确调用 implement 时使用；其默认测试/审查不能扩大本次授权 |
| 明确要求优化提示词或整理给另一个 AI 的交接内容 | 使用 prompt-engineering，保持原意；只要求优化就只输出提示词 |
| 复杂、跨步骤、高风险或需求草稿化 | 主代理按 prompt-engineering 执行模式内部整理目标、上下文、约束、验收点和输出边界后直接执行；不展示提示词稿、不等待确认；不补造关键规则或扩大授权 |
| 简单、明确且低风险的实现指令 | 直接执行，不套提示词流程，也不额外生成一份提示词让用户复制 |
| 新建或改版页面、列表/表单/弹窗/看板、样式与布局调整 | 按 `frontend-design` 定方向：业务 CRUD 页走「既有设计系统增强」，独立看板/展示页可自由设计；项目有 UI 规范时以项目规范为准 |
| 页面效果/功能快检 | 用户明确要求时使用现有浏览器能力；明确目标环境、账号、路径与数据操作边界 |
| “审查一下、review、把关” | 默认主代理轻审当前改动和必要依赖，不自动套用三视角 review |
| “独立审查、认真检查” | 主代理按独立审查清单检查指定 diff/提交范围，报告问题、证据和未验证项；不启动子代理 |
| “完整审查、三视角审查”或显式调用 review 技能 | 调用已有 review 技能；由主代理分别完成三种审查视角，测试与外部写入仍须对应授权 |
| “页面快检”或明确要求检查页面 | 主代理直接使用现有浏览器工具检查指定路径；不启动子代理 |
| “实现并验证”“做完并验证” | 默认只编译受影响的前后端；额外检查按用户明确范围执行 |
| “可以交付”“验收”“发版前检查” | 编译受影响的前后端；UI 可见改动再按 `page-acceptance` 走页面验收；额外测试需用户明确要求 |

技能不可用时说明并用能完成任务的现有能力处理，不假称调用。不要因 review/implement 的宽泛描述自动启动重流程。

技能正文可能提到未随当前资源库安装的可选技能（例如架构审查或写作技能）。这些名称不是隐式依赖：只有实际安装并通过入口确认可用时才读取；缺失时用当前技能的直接实现/审查步骤完成，并记录未覆盖的能力，不阻塞主任务。

## 固定交付流程

实现或修复形成可交付改动后，默认走最短可行路径。纯咨询、审查、规划或用户明确暂缓时不进入收尾。

1. **核对改动**：主代理核对本次 diff、必要调用关系和未测项。
2. **按需检查**：编译受影响的前后端；UI 可见改动按 `page-acceptance` 走页面验收，非 UI 改动不做；中高风险、跨模块、权限/数据/契约变化或用户要求独立审查时，按独立审查清单逐项核对，不把主代理自审说成外部独立结论。
3. **文档与 Git**：主代理直接更新受影响的运行态文档，完成暂存、提交，并推送到已有正常上游。

文档、暂存、提交、推送共享同一工作区，必须由主代理按顺序完成；不并行启动其他写者。

## 测试与修正

默认检查本次改动涉及的前后端能否编译。前后端均有改动时分别编译；仅改一端时只编译该端，纯文档或不影响编译的配置改动只核对差异。复用项目已有编译/构建命令，跳过测试，不独立运行 lint 或自动化测试；已有构建命令内置的编译类型检查可保留。用户明确要求额外检查或暂不编译时按当次要求执行。编译失败或环境缺失时如实报告，不把编译通过等同于功能验收。

**页面验收的触发面**：改动在界面上可见时（页面、列表、表单、弹窗、看板、权限相关控件、样式布局）按 `page-acceptance` 执行；接口、后端逻辑、文档、构建配置等界面不可见的改动不触发。环境、账号、数据或工具不可用时按该技能报告 blocked 或未运行项，不以「默认只编译」把 UI 改动直接判为完成。

用户已要求的检查失败、未完成或被阻塞时，不以默认策略免除该要求。报告已完成部分和具体阻塞，不把任务标为全部完成；不重复未受后续改动影响的已通过检查。

页面验收是一条主路径加一个相关边界；失败时查相关控制台/请求并按需截图，不默认全站回归。缺少服务、账号或测试数据则报告，不自行扩大到部署或生产操作。

页面美化方向按 `frontend-design` 确定；项目登记了 UI 规范时以其为准，业务页与独立展示页分别对待。视觉与交互结论以渲染结果为依据，不以源码判断。

用户要求修复并允许复测时，主代理修正后只复测受影响路径；审查报告本身不授权修改。修改后旧证据不覆盖新版本。用户说测试通过时标为“用户确认”，不冒充 AI 实测。

## 完成与收尾

实现、修复或文档任务完成，或者当前任务中用户说“测试没问题/可以收尾”时，进入此阶段；纯咨询、审查或提示词优化不触发。

1. 自动检查文档影响。API、配置、权限、数据结构、操作步骤或重要决策变化时更新直接相关的现有文档；已配置状态文件时，只同步真实变化的状态、决策或验证证据。文档仍准确就不凑数新增。不要擅改远程 Issue。不把未验证状态写成已验收。
2. 提交前检查 `git diff --cached --name-status`，并与进入任务时记录的暂存区基线比较。若存在本任务开始前已有或归属不明的暂存内容，保留索引并停止自动提交；不尝试清理或绕过。无既有暂存时，只暂存明确属于本任务的路径，再检查 `git diff --cached` 的文件清单与差异，仅在全部属于本任务时提交。禁止用全库暂存代替归属核对。混杂工作区无法可靠区分、冲突/变基或无提交身份时，同样停止并报告。非 Git 工程保留文件并说明。
3. 在创建自动本地提交前，对已暂存差异运行本技能的 `scripts/scan-staged-secrets.py`。它只报告高置信度凭证模式；发现结果时停止提交、不要在报告中回显秘密，并让用户替换或移出凭证后再继续。检查提交钩子及实际差异；钩子要求未授权验证时不擅跑、不绕过。已要求的必要验证失败、未完成或被阻塞时暂停自动提交，先处理或报告；用户明确要求保留中间提交时可按该授权提交，但不得标记已验收。用户说“先别提交/先别改文档”或项目有更严格要求时遵循。
4. 简短报告改了什么、实际验证结果、未测项、文档是否更新、提交哈希、推送目标或未推送原因。只有当前分支存在正常上游、不是受保护/默认分支、项目规则允许且本次授权覆盖推送时才普通 push；推送后核验远端引用与本地 HEAD 一致，并确认 `@{u}` 可解析到对应 remote-tracking 分支。单分支浅克隆或首次推送可能只写入 branch.remote/branch.merge 而不建立 remote-tracking，此时先补齐普通 fetch refspec（`+refs/heads/*:refs/remotes/<remote>/*`）并 fetch 复验，再报告已推送；不得把 push 返回成功直接当成上游可用。不自动合并、发布、部署，不强推或改写历史。

自动本地提交是协作授权与判断流程，由主代理按指令执行。独立任务完成时可提交；用户要先看页面再提交，遵循其“先别提交”，之后明确“可以收尾”再提交。

## 资源库自检与维护

资源库是跨项目复用的源；Codex 的 `AGENTS.md` 和技能副本是生成结果。修改资源库后先运行：

```powershell
magpie library sync
python C:\Users\s1a71\.config\magpie\library\skills\engineering-workflow\scripts\verify-library.py
```

健康检查只验证结构、同步和哈希，不验证 MCP 连通性、模型供应商、插件运行状态或项目业务测试。发现技能副本或指令不一致时先修复源配置并重新同步，不要直接改生成副本掩盖问题。MCP 报传输错误时先核对 Magpie 端口和当前 Codex 会话，不能把“服务在监听”当成“本会话已连通”。插件和模型组属于 Magpie 运行配置，不由本技能假装管理。
## 工具分工

MCP 是工具而非自动任务：浏览器用于界面；文档工具用于版本依据；数据库/SSH 先核对目标环境与操作范围。已有连接不代表授权写入，不主动巡检所有服务。

工具不可用、超时或报错时依据实际错误采取有界处理，不无变化重试或伪造成功；替代方式须保持原有授权边界。缺失必要工具需安装、联网付费或扩大权限时，先报告具体条件。部署/数据库写入按明确授权、影响范围与必要回退条件执行，复用已有方案，不另外强建发布框架。

RTK 保留终端输出压缩。各 Agent 的模型与工具选择沿用现有配置，本技能不重写路由。

需要完整使用说明或换项目示例时，读取 [使用指南](references/usage.md)。

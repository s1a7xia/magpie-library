# 问 Matt：工作流导航

你不需要记住每个技能。先读项目 `AGENTS.md`、相关代码、术语表、ADR、状态文档和当前授权，再从这里选择**最短充分路径**。

这个技能只负责路由，不直接实现、不扩权、不把完整流程强加给简单任务。Codex 已知当前可用技能时直接使用对应技能；只有路径不清、需要跨阶段取舍时，才说明为什么需要本技能，并在用户确认后读取和执行这里。

**只推荐当前 Magpie 资源库实际安装的技能。** 如果下面的表里没有，说明当前资源库不提供，不要凭上游仓库或旧文档假装它可用。

这些技能都来自 Magpie 资源库。15 个直接技能位于 `~/.codex/skills`，在 Codex 中用短名调用，例如 `$wayfinder`、`$to-tickets`；`triage`、`retro`、`handoff`、`writing-for-agents` 这 4 个低频技能经 `magpie-skills` 聚合入口读取，不假设存在 `$triage` 等独立快捷入口。当前只有 `ruoyi6`、`database-design`、`grill-with-docs` 可隐式触发。

## 授权门

技能调用不等于授权。开始前落实当前任务已经授予的范围：

- 默认在当前会话完成；全局不主动派子代理。`grilling`、`research` 或 `wayfinder` 获准进入后，才按各自 `SKILL.md` 的定义授权其所需子代理，无需再次确认；该授权不自动扩展到其他技能。实现始终由当前会话直接完成，不另设实现技能、worktree 或实现者子代理。分支、提交、push 和 PR 仍按当前任务边界执行。
- Issue/PR 的创建、评论、标签、关闭、合并，以及提交、push、发布、部署，需要明确授权。
- 测试、TDD、构建和页面运行验收按当前任务明确要求执行；实现或修复本身不自动授予测试权限。
- 数据库结构变更、权限扩大、不可逆写入、资金和凭证操作需要单独授权。
- 没有外部 tracker 授权时，规格、tickets 和 wayfinder 决策图使用项目内本地 Markdown，不写远端。

## 主流程：需求 -> 可靠交付

### 0. 先建立事实基线

读项目规则、相关代码、调用链、现有术语/ADR、状态文档和 Git 事实；明确目标、验收、风险、授权和停止条件。没有证据的假设要标出来，外部事实不明时读取 `../research/SKILL.md` 并在当前决策中带回结论；需要单独启动调研流程时，提示用户调用 `$research`。

### 1. 选择路径

- **目标、验收和修改位置都清楚**：直接实现，不建流程工件。
- **当前会话能消除歧义**：`grill-with-docs`。讨论到持久化模型时叠加 `database-design`；RuoYi 实现阶段叠加 `ruoyi6`。
- **需要事实**：读取 `../research/SKILL.md`，把结论带回当前决策；需要独立调研流程时显式调用 `$research`。
- **需要看效果**：读取 `../prototype/SKILL.md`，用一次性样品回答问题，再回到决策；需要独立原型流程时显式调用 `$prototype`。
- **大型、跨会话、关键未知互相阻塞**：先建议 `$wayfinder`，用户确认后建立决策地图。它只产出决策和路线，不直接交付功能。

### 2. 收敛为规格

路线清楚后，用 `$to-spec` 把已确认内容收束成可验收 spec。spec 至少写明：目标、范围外、业务规则、数据契约、接口/页面影响、权限、失败路径、验收证据和未决项。

只有同时存在多个可独立交付的纵向切片或真实阻塞依赖时才建议 `$to-tickets`，用户确认后再拆；单切片任务不要为了仪式感拆票。

### 3. 实现

- **实现**：当前 Codex 会话直接实现，遵循项目规范，复用现有能力。有 spec 或 tickets 时按顺序一次处理一个 ticket 或最小充分切片；不启动子代理、不创建 worktree，也不自动测试、审查或提交。
- **测试**：只有用户明确要求测试、TDD 或运行验证时才执行对应测试；当前资源库未提供 `tdd` 技能，不声称调用它。未授权时不要自行新增或运行测试。
- 每完成一个切片，核对行为、受影响的调用链、文档和持久化结果；不把“代码写完”当成“已验收”。

### 4. 验收与审查

按用户可观察的结果报告实际证据：测试/构建结果、页面路径、数据库只读证据或明确的人工确认。未运行的验证必须标为未验证。

仅在用户明确要求 `$code-review` 时执行规范与规格双轴审查。显式调用即授权启动两个并行的只读 Standards/Spec 审查子代理，无需再次确认；若当前环境无法并行，则在当前会话串行完成两轴并明确标记为降级执行。该授权不包含修改、测试、提交、部署或扩大任务范围。

`grilling`、`research`、`wayfinder` 同理：技能自身定义的子代理由显式调用该技能授权，但只限其正文明示的只读调查范围；不得借此启动其他后台代理或扩大 Git、测试、外部写入授权。

### 5. 复盘

`retro` 只在用户要求时使用。它改进的是 agent 环境、导航指针、确定性检查和编码标准，不擅自重构产品代码。

## 入口匝道

- **外部需求或缺陷堆积**：`triage`。它只处理不是你刚创建的原始输入；`to-tickets` 产出的 tickets 已经 agent-ready，不再 triage。
- **项目里出现困难缺陷**：当前资源库没有 `diagnosing-bugs`；按当前项目规则直接定位根因，必要时用 `research` 或 `prototype` 获取证据，不要假装缺失技能存在。
- **巨大且模糊的项目**：`wayfinder` 建立共享决策地图。地图清楚后先 `to-spec`，再按实际需要 `to-tickets`，不要从地图直接猛冲实现。

## 阶段边界

在一个阶段真正结束时选择：继续、开新会话、`handoff`、授权子代理，或按宿主能力压缩上下文。需要完整判断树时读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md)。

`handoff` 只买到可携带性：换 harness、换目录、交给同事，或阶段中途分叉任务时才需要。不要为留在同一目录、同一会话的普通续接制造交接文件。

## 输出格式

给出简短路线即可：

1. 当前判断与理由；
2. 下一步只调用哪个技能；
3. 需要的输入/产物；
4. 授权门和不能做的事；
5. 停止条件与验收证据。

不要一次列出整条流水线让用户逐项确认；默认推进到当前授权范围内最有价值的下一步。

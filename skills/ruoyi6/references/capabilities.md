# 框架能力选型

## 怎么用

业务判型之后、动手写代码之前，用这份表做一次**机制扫描**：需求里出现了哪些信号，就先确认对应能力是否已经存在，再决定用不用。

这不是要每项都上。命中信号才看，没命中就跳过；确实需要才引入，没有验收标准不要为了“以后可能”预埋。

## 先看这四类（按本项目实际使用频率）

`ruoyi-system`（作者核心模块）和 `ruoyi-demo`（官方示例）里最常见的是这四类，普通业务模块绝大多数只需要它们：

| 能力 | 先看 | 什么时候用 |
|---|---|---|
| `@Log` 操作日志 | 作者 Controller 的对应场景 | 用户触发的增删改及关键状态变更；导入/导出按作者对应场景记录 |
| `@Transactional` | 作者 Service 的多写场景 | 一次请求写多张表或多处 |
| `@RepeatSubmit` 防重 | 作者表单写入口 | 表单、按钮、导入等可重复提交入口 |
| 分组校验 | 作者 BO 和 Controller | 新增用 `AddGroup`、修改用 `EditGroup`、查询用 `QueryGroup` |

举例说明这三个分组各自管什么：新增和修改的必填项常常不同（新增要密码、修改不要），所以 BO 字段上的 `@NotBlank(groups = AddGroup.class)` 只在新增生效；查询条件通常都是可选，`QueryGroup` 让它们不参与必填校验。`ruoyi-system` 的 `SysOssConfigController`、`ruoyi-demo` 的 `TestDemoController` 都是 `list(@Validated(QueryGroup.class) ...)` 的真实写法。

下面各类按需查，不要为了“看起来完整”全部引入。

## 一、写入与一致性

| 信号 | 先看 | 判断要点 |
|---|---|---|
| 一次请求写多张表、多次写库 | `@Transactional(rollbackFor = Exception.class)` | 标在 Service 公共方法上；同类内部调用不生效 |
| 单表一次写入 | 不必加事务 | 加事务也有成本，别机械套 |
| 跨数据源或远程调用 | 事务边界分开，配补偿或最终一致 | 不要在事务里做远程调用和长耗时操作 |
| 需要回滚但已被 try 捕获 | 异常要抛出或显式回滚 | 吞异常等于事务失效 |
| 并发改同一行 | `@Version` 乐观锁、条件更新 | 检查影响行数，返回冲突提示 |
| 并发抢同一资源 | `@Lock4j` 分布式锁 | 锁粒度最小、必须有超时 |

## 二、请求入口防护

| 信号 | 先看 | 判断要点 |
|---|---|---|
| 表单/按钮重复提交 | `@RepeatSubmit` | Redis 短时窗口，默认 5 秒；只防短时重复，不是业务幂等 |
| 业务唯一键不能重复 | 数据库唯一约束 | 优先级最高，应用层校验只是前置提示 |
| 外部回调、消息重复投递 | 业务幂等表或幂等键 | 需要跨天/跨重启仍然有效，不能只靠 Redis |
| 高频接口被刷 | `@RateLimiter` | 按 key、次数、时间窗配置；区分用户级和接口级 |
| 批量或导入接口 | 限流 + 批大小控制 | 一次请求不要无限量写入 |

**幂等的选择顺序**：数据库唯一约束 → 业务幂等表（记录已处理键）→ `@RepeatSubmit`（只防短时）→ 前端按钮禁用（只是体验，不是保障）。不能用后者替代前者。

## 三、读性能与缓存

| 信号 | 先看 | 判断要点 |
|---|---|---|
| 高频读、变化少 | `@Cacheable` / `@CacheEvict` + `CacheNames` | 与 Spring Cache 联动，缓存名统一登记 |
| 需要手动控制读写 | `RedisUtils` | 自行管理 key 和 TTL |
| 本地热点、可容忍短暂不一致 | `CacheNames` 缓存名的 `#local` 参数（默认 1，置 0 关闭） | 由 `PlusSpringCacheManager` 组合本地 Caffeine 与远端缓存；不要把内部装饰器当业务入口 |
| 慢查询 | 先看索引和执行计划 | **不要用缓存掩盖索引缺失** |
| 列表/导出数据量大 | 分页、按需字段、批量查询 | 避免 N+1 和无界查询 |
| 写操作命中已有缓存 | 同步失效 | 只改库不改缓存会产生脏读 |

**缓存的判断顺序**：能否加索引 → 能否减少查询 → 能否批量 → 最后才考虑缓存。缓存是最后一层，不是第一反应。

## 四、异步与解耦

| 信号 | 先看 | 判断要点 |
|---|---|---|
| 响应要快、后续可异步 | `@Async` | 需配置线程池；异常不会传回调用方，要自己记日志 |
| 需要排队、削峰 | `QueueUtils` | Redis 队列，注意消费失败和重试 |
| 定时/周期执行 | 定时任务执行器 | 任务必须幂等可重入 |
| 跨模块解耦通知 | 消息（`MessageService`） | 实时推送不落库；消息盒子才落库 |
| 大量并发短任务 | `ThreadUtils` / 线程池 | 不要每次 `new Thread` |
| 需要进度或推送 | `PushHelper`（SSE / WebSocket） | 复用现有传输，不自建长连接 |

**异步的判断顺序**：同步能否接受 → 事务提交后再异步 → 队列 → 定时任务 → 消息中间件。不要一上来就上 MQ。

## 五、并发与线程

| 信号 | 先看 | 判断要点 |
|---|---|---|
| 批量并行处理 | `ThreadUtils` 或现有线程池 | 控制并发度，避免打满数据库连接池 |
| 需要传递登录态 | 显式设置用户上下文 | 异步线程默认没有 `LoginHelper` 上下文 |
| 任务超时 | 设置超时和中断处理 | 不要无限等待 |
| 结果聚合 | `CompletableFuture` | 注意异常传播和线程池隔离 |

## 六、状态与流程编排

| 信号 | 先看 | 判断要点 |
|---|---|---|
| 简单状态流转 | 业务显式状态字段 + 合法迁移校验 | 不要为 3 个状态引入流程引擎 |
| 多步骤、可配置编排 | `ruoyi-common-liteflow` | 组件化编排，规则可配 |
| 人工审批 | `WorkflowService` | 见 `optional-integrations.md` |
| 需要事件驱动 | Spring 事件或消息 | 简单解耦用事件，跨服务用消息 |

## 七、编号、序列与唯一标识

| 信号 | 先看 | 判断要点 |
|---|---|---|
| 业务流水号 | `SequenceUtils` | 按前缀生成，注意并发和日期段 |
| 主键 | 雪花 ID（`IdGeneratorUtil` / MP 默认） | 前端用 `string \| number` |
| 对外单号 | 独立字段 + 唯一约束 | 不要复用主键当业务单号 |

## 八、数据展示与导出

| 信号 | 先看 | 判断要点 |
|---|---|---|
| 展示用户/部门/字典名 | `@Translation` | 列表批量翻译，避免 N+1 |
| 敏感字段 | `@Sensitive`（标 VO） | 只影响序列化，不是存储加密 |
| 存储加密 | `@EncryptField` | 字段级加解密，注意查询条件 |
| 接口传输加密 | `@ApiEncrypt` | 需前后端同时开启 |
| 导入导出 | `ExcelBuilder`、`@ExcelProperty` | 大文件分批，导入用独立 ImportVo |
| 字典转换 | `@ExcelDictFormat` | 与 `sys_dict_*` 对应 |
| 大数字精度 | `BigNumberSerializer` | 雪花 ID 序列化为字符串 |

## 九、外部接入与通信

| 信号 | 先看 | 判断要点 |
|---|---|---|
| 文件上传下载 | `OssClient`、`OssFactory` | 存 `ossId`，不存临时 URL |
| 发邮件 | `MailBuilder` | 异步发送，不阻塞主流程 |
| 发短信 | `PlusSmsDao` | 注意频控和模板 |
| MQTT | `MqttClientGlobalMessageListener` | 连接和重连交给框架 |
| 第三方 API | 独立适配器 | 超时、重试、熔断明确 |

## 十、审计与可观测

| 信号 | 先看 | 判断要点 |
|---|---|---|
| 用户触发的业务操作 | `@Log` + `BusinessType` | 按作者对应场景记录操作人和结果；导出属于可审计操作，但不是数据写入 |
| 业务异常 | `ServiceException` + 国际化消息 | 不吞异常，不返回裸字符串 |
| 需要排查慢接口 | 现有日志和耗时拦截 | 不在业务代码里自建监控 |
| 重要状态变更的长期追溯 | 业务历史表或审计字段 | `@Log` 是操作日志，不保证提供业务状态前后值、版本比较或长期留存 |

## 容易漏掉的几条

- **事务 + 异步**：事务未提交就发异步，异步侧可能读不到数据。要在提交后触发。
- **事务 + 远程调用**：远程失败会拖长事务，甚至回滚不了外部副作用。
- **缓存 + 数据权限**：带数据范围的列表不要直接缓存，不同用户看到的数据不同。
- **幂等 + 事务**：幂等记录要和业务写入在同一事务，否则会出现“记了但没做”。
- **锁 + 事务**：锁的范围要包住事务，不能锁在事务内部方法上。
- **逻辑删除 + 唯一索引**：删除后同值重建会冲突，需要评估索引设计。
- **异步 + 登录态**：异步线程拿不到当前用户，要显式传用户 ID。

## 检查

- [ ] 已按需求信号扫过上面十类，命中的项都确认了现有能力。
- [ ] 没有为了“以后可能用到”预埋事务、缓存、队列或幂等表。
- [ ] 事务、幂等、缓存、异步的选择有明确理由，不是惯性套用。
- [ ] 写入、读取、异步、并发之间的组合陷阱已考虑。
- [ ] 因业务未定而暂缓引入的能力（如审批、异步、缓存）已记为 TODO，并说明触发条件，不留在“可能以后要做”的模糊状态。

## 新增能力前的门槛

想新写一个东西之前，先确认它不属于已有能力。不同对象的门槛不一样：

| 想新增 | 必须先满足 | 参考放哪 |
|---|---|---|
| 公共工具方法 | 至少两个模块会用到，且语义稳定；单业务规则留在业务 Service | `ruoyi-common-core` |
| 新的 `ruoyi-common-*` 模块 | 有独立依赖、配置和装配条件，且现有模块塞不进 | 新建模块，同时更新 `ruoyi-common/pom.xml` 和 `ruoyi-admin` |
| 跨模块 API | 有两个及以上模块要调用同一能力，且已有 `ruoyi-api` 接口无法扩展 | `ruoyi-api`，只放接口和 DTO |
| 全局前端组件 | 至少两个真实页面会用；单页结构留在页面目录 | `plus-ui-React/src/components/common` |
| 新 hook | 现有 hook 无法组合或薄包装解决，且只承载页面行为 | `plus-ui-React/src/hooks` |
| 业务表 | 现有表加字段或状态无法表达，且满足单表优先原则 | 项目登记的 SQL 目录；没有登记时先确认落点 |
| 字典 | 值是有限枚举且需要界面选择和翻译 | `sys_dict_type` + `sys_dict_data` |
| 参数 | 值需要运行期修改，不是枚举 | `sys_config` |

做不到“至少两个调用方”时，先留在本业务模块，等第二个真实调用方出现再提升。不要为了对称或“架构完整”提前抽象。

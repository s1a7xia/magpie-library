# Review

本阶段只能由用户单独明确发起；端到端开发授权、上一阶段完成或工作流自动续接都不能启动本阶段。

用户显式发起的完整审查。主代理从验证证据、代码正确性、影响范围三个角度检查同一批改动，输出一份按严重程度排序的报告。共享上下文读一次；仅在文件变化、证据不足或恢复会话时重读，不用重复读取模拟独立审查。

## 执行

1. 按 [入口协议](../rules/entry-protocol.md) 读取相关项目事实与规范。遵守项目 profile 选择（含 `none`）；仅适用的 RuoYi 代码/契约范围加载 `ruoyi6` 与相关 reference；涉及新表、表关系、唯一性、删除语义、索引或迁移时按项目配置的数据库设计入口执行（未配置时为 `database-design`）。先声明审查范围：优先用 PRD/verification 中本批起止提交和切片提交清单，再纳入属于本次范围的未提交改动。单分支开发不能默认用 `main..HEAD`；范围不明时查提交记录，仍无法确定才询问。详见 [范围与检查参考](REFERENCE.md)。
2. 核对本批提交与编译等已有证据。页面验收不是 review 的前置门槛；UI 范围尚未验收时记录待验收，非 UI 范围记 `Page acceptance: N/A — <reason>`。已有验收仅在覆盖当前行为时复用，代码审查不证明页面可用。
3. 检查三个角度：验证证据是否真实且适用；代码是否满足需求与框架约定；调用方、数据、权限和跨切片交互是否受破坏。只检查本次范围相关风险；默认不新增或运行测试、lint、独立类型检查，不自动运行构建；仅当前请求授权或更高优先级指令要求时执行最小检查，已有有效证据不重复。
4. 合并重复发现。每条问题给出位置、触发条件、实际后果和修复建议；证据不足标为待确认。不同角度结论冲突时先核实事实，只有必须由人决定的业务取舍才提问。不强制三份报告或批准提问。
5. 一轮 review 内按既定三角度顺序检查完整范围。确认缺陷在已授权范围内立即登记并进入 [debug](../debug/SKILL.md) 修复；用户明确只读审查时只报告。修复后继续检查剩余角度和剩余范围，不因单个修复提前结束整轮 review。风格、重构或设计建议不自动实施；修复超出已授权范围时停止受影响工作。
6. 阶段顺序与证据回流见 [共享契约](../rules/workflow-contract.md#4-验收门槛与回流)：默认先手动 review，再手动页面验收；首次覆盖完整声明范围，不自动启动下一阶段。
7. 将本轮最终代码范围、发现、修复、实际检查与 review 结论写入 verification，并更新相关状态。UI 未验收保持 `Dev Complete`；验收已通过但 review 尚不覆盖最终代码时保持 `Accepted`；两项证据有效且收尾完成才写 `Done`。只读请求不改文件或状态。

## 交付

报告审查提交范围、按严重程度排序的发现、修复情况、实际检查/未验证项、状态与下一步。

结束明确报告：review 是否覆盖修复后的最终代码；UI 尚未验收则 `Next (user-initiated): /page-acceptance`；无 UI 或验收证据仍有效且收尾完成则写回 `Done`；未通过保留实际状态和阻塞。

无问题就直说未发现问题，同时说明审查覆盖边界。只同步直接相关文档，提交与推送遵循项目约定和当前授权；不自动发布 Issue、建 PR、合并或部署。

详细检查按需读 [REFERENCE.md](REFERENCE.md)，不为普通轻审加载本技能。

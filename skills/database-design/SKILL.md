# 数据库设计与落表

本技能是关系型数据库建模、落表和迁移评审的唯一入口。目标不是产出 `CREATE TABLE`，而是形成代码、约束和查询能共同维护的数据契约；先证明现有模型为什么不够，再决定表、字段、键、索引和迁移。

它同时也是数据库变更的准入守门，而不是只在需求讨论阶段使用的设计助手。需求、表名和业务规则已经批准后，仍然要经过本技能，但只做**增量契约核对**：按已批准的范围检查复用、DDL、字段链路、字典/参数、索引和迁移，不重新发散需求，也不重开已经确认的产品方案。只有发现已批准契约本身冲突、关键事实缺失或需要扩大范围时，才停下来请用户裁决。

## 先加载事实

按任务实际范围取证，不凭印象设计：

1. 项目 `AGENTS.md`、编码规范、已有 PRD/数据模型文档。
2. 真实数据库的 schema、版本、方言、迁移脚本和执行记录。
3. 现有表、列、主键、外键、唯一/检查约束、索引、注释和数据分布。
4. 真实写入、查询、分页、排序、导出、权限和后台任务路径。
5. 当前 checkout 的 Entity、BO/VO、TypeHandler、字典和参数调用。

项目专用数据库规则和 PostgreSQL 技术参考只读取适用部分；它们是事实或裁决来源，不是第二套数据库设计入口。

## 必须先过准入

工作量按变更类型分级。分级只决定检查深度，不把“任务已定稿”当成跳过数据库准入的理由。

| 变更类型 | 必做检查 | 不再做的事 |
|---|---|---|
| 纯读取、只查现有模型、不改 DDL/DML | 查询真实 schema 和调用链；说明是否命中已有表、字典、参数 | 不生成契约、不要求新表审批 |
| 已批准的简单增量：现有表加普通字段、补索引、补字典项 | 轻量增量契约：复用结论、字段语义/类型/可空/默认值、字典或参数复用、DDL 落点、Entity/BO/VO/TS/页面链路、迁移与回滚 | 不重做完整业务判型，不重新讨论已批准需求 |
| 新表、改关系/唯一性/删除语义/生命周期/历史策略、JSONB 模型、复杂迁移 | 完整数据模型契约和五项硬门槛 | 不在未批准表名前写正式建表迁移 |
| 只读 review 或 debug | 核对实际结构与已批准契约、调用链和风险 | 不顺手重构存量，不自动写库 |

轻量增量不等于随意建字段：如果新增字段改变业务身份、归属、唯一性、状态机、删除语义或历史保留，升级为完整契约。

准备新增业务表，或改变表关系、唯一性、可空性、删除语义、历史保留、索引模型或迁移时，先写出数据模型契约。先改开发库再补说明、用万能 JSON/EAV 代替建模、以“以后再迁移”推迟决定，均不算通过。

### 五项硬门槛

1. **复用结论**：扫描现有表、字段、字典、参数、菜单和增量脚本，说明为什么不能复用或扩展。只写“没有合适的表”不算证据。
2. **表角色与业务身份**：说明一行代表什么、如何唯一识别、归属谁；一张表只承担一个主要角色。
3. **生命周期与删除语义**：产生、状态迁移、终态、归档/删除、保留期限，以及被引用时怎么办。
4. **不变量与唯一性**：必须永远成立的规则，以及 `NOT NULL`、`UNIQUE`、`CHECK`、外键或事务维护的落点。
5. **迁移与可追溯性**：增量脚本路径、已有数据补值、兼容窗口、失败恢复和回滚依据。源码中找不到创建/迁移来源的新表不得声称交付完成。

### 表角色

| 角色 | 一行代表 | 重点 |
|---|---|---|
| 核心实体 | 一个独立业务对象 | 稳定身份、归属、状态、唯一键、引用行为 |
| 明细/关系 | 主体下的一条明细或多对多关系 | 复合唯一键、级联/禁止删除、关系属性 |
| 来源原始事实 | 一次外部输入、采集或事件载荷 | 来源幂等键、原始值不可变、去重与重放 |
| 规范化结果 | 从原始事实解析出的标准对象 | 与来源的追溯关系、解析版本、可重算性 |
| 派生统计/评分 | 某口径、时间窗或版本的聚合 | 口径与维度唯一、可重算、过期策略 |
| 流程/任务 | 一次可执行流程、步骤或任务 | 状态机、并发抢占、重试、终态与恢复 |
| 历史/审计 | 某对象在某一时点的快照或操作记录 | 只追加、保留期限、查询维度、不可篡改边界 |
| 临时请求/导出 | 一次性请求、异步导出或临时批次 | 过期清理、幂等、与正式业务数据隔离 |

同时承担原始载荷、规范化字段、当前状态、派生统计、历史快照中的三类以上时，优先怀疑职责混杂，而不是继续加字段。

### 契约模板

写入项目实际使用的 PRD、切片或迁移脚本头部，不新建第二套模型文档：

```text
Data Model Contract
- 复用结论：现有表/字段/字典/参数为何不足
- 表角色与业务身份：一行代表什么，如何唯一识别，归属谁
- 关系与基数：1:1、1:N、N:M；是否允许为空或转移
- 不变量：必须始终成立、不能只靠页面校验的规则
- 唯一与幂等：业务唯一键、外部单号、导入批次或幂等键
- 生命周期与删除：状态、合法迁移、终态、归档/删除及引用行为
- 查询与索引：主要查询、过滤、排序、分页、导出及索引依据
- 容量与并发：增长、读写比例、锁、冲突和异步边界
- 迁移与回滚：已有数据补值、兼容窗口、失败恢复、可逆性
- 未决项：待确认什么、当前推荐实现、影响和确认人
```

可用本技能目录的 `scripts/check_model_contract.py` 做只读字段完整性检查；通过只表示没有漏写，不证明建模正确。

需要展开评审顺序、反模式、唯一性/删除细节或评审结论格式时，读取 [references/model-review.md](references/model-review.md)。

## 建模判断

### 复用与拆表

- 默认单表。先尝试现有表加列、状态或关联。
- 用户、部门、角色、岗位、字典、参数、文件优先复用 `sys_user`、`sys_dept`、`sys_role`、`sys_post`、`sys_dict_*`、`sys_config`、`sys_oss`。
- 可枚举状态/类型用 `sys_dict_*`；运行期开关、阈值、周期用 `sys_config`；业务记录才建表。
- 稳定的身份、归属、权限、业务唯一键、关键状态和频繁筛选/排序值落真实列，不藏在 JSON。
- 只有以下至少一项成立才拆子表：可重复的结构化明细、需要数据库关系约束、独立生命周期/权限/查询边界/数据量，或不拆会产生无界重复组或无法约束的状态。
- 不为未来可能性预建主从表、通用扩展表、事件表或版本表。

### 键、约束与删除

- 每张业务表有稳定主键；主键和关联 ID 按项目既有 ID 契约设计。
- 业务唯一性优先数据库唯一约束；服务层先查后写不能替代并发唯一性。
- 可空性、默认值和 `CHECK` 表达真实业务规则；跨行/跨表唯一用复合唯一约束，引用完整性用外键或明确的事务/清理责任。
- 金额用明确精度的 `numeric`/`decimal`，不用浮点。
- 删除逐关系明确：禁止、级联、置空、逻辑删除、归档/注销。不要默认所有表都加 `del_flag`。
- 逻辑删除要检查唯一约束：删除后是否允许同值重建；必要时用部分唯一索引或项目既有方案。
- 并发更新需要 `version`、条件更新或锁时，定义冲突返回并检查影响行数。
- `@Log` 不等于业务历史；需要恢复、审计或合规留痕时明确保留期限和查询维度。

### 查询与索引

为主要查询写清过滤、排序、分页和索引；没有查询依据的索引只是猜测。

- 等值条件在前，范围条件通常在后；评估数据权限/归属列是否应作前导列。
- 评估逻辑删除和状态过滤是否适合部分索引。
- 已有主键或唯一索引的前缀能覆盖时，不重复建索引。
- 低选择性字段不单独建索引；写入频率高的表控制索引数量。
- 外键不自动带索引，按连接、级联和子记录查询需要决定。
- 无界 `LIKE '%keyword%'` 不假设索引可扩展；导出和批量操作不能无界扫全表。

### JSONB

JSONB 只用于真正稀疏、结构可变、不参与关键约束或高频筛选的属性，以及外部原始载荷和审计快照。

- 需要 `NOT NULL`、`CHECK`、外键、唯一性或频繁连接/排序/聚合的值，提升为真实列。
- 明确结构、类型、大小边界和版本；在 BO/Service 校验，不用任意 Map 掩盖业务规则。
- 定义未传、SQL NULL、JSON null、空对象和删除属性的区别；明确整文档替换或局部更新。
- 包含查询按实际运算符评估 GIN，不默认每列建索引；PostgreSQL 的 GIN 不恢复普通列约束和统计信息。
- 不把无限增长的扫描历史、操作流水或明细集合塞进主表数组。

## PostgreSQL 与 RuoYi 落表

以下规则只在项目使用 PostgreSQL / RuoYi-Vue-Plus 时适用；项目专用规则和当前 checkout 优先。通用 RuoYi 字段链路和源码落点在 `ruoyi6` 中核对，本技能负责数据模型、DDL 契约和迁移判断。

### 命名与字段

- 表、列、约束和索引使用不加双引号的小写 `snake_case`；标识符默认不超过 63 字节。
- 主键默认 `id`；雪花 ID 用 `bigint` / `Long`，前端精度处理按 `ruoyi6` 的当前约定核对。
- 继承 `BaseEntity` 的审计列按当前真实基类和自动填充器核对，不机械增加项目没有的隔离字段或 `del_flag`。
- 金额用明确精度；字符串长度按真实业务约束，不统一 `varchar(255)`。
- 新表和新增字段写数据库注释，术语与页面、字典、Java 字段一致；审计时查 `obj_description` / `col_description`，不能拿 Entity JavaDoc 冒充数据库注释。
- 时间类型沿用项目已确认的 JDBC、序列化和存量时区契约；未完成验证前不擅自混用 `timestamp` 与 `timestamptz`。PostgreSQL 的 `timestamptz` 是时间点，`timestamp` 是无时区墙上时间。
- 状态/标志沿用项目已确认的一种表达并贯通 Entity/BO/VO、默认值和 DDL；同一业务域不混用 `char(1)`、`boolean` 和字符串字典值。
- 非空、默认值、唯一和检查约束按业务明确；新增必填列先设计已有数据补值，不能直接加无默认值的 `NOT NULL`。

### 字段链路

新增或修改字段时，至少核对实际受影响项：

```text
DDL / 增量 SQL
  -> Entity（@TableField、类型、逻辑删除/版本）
  -> BO（新增/编辑校验分组）
  -> VO（列表、Excel、翻译、脱敏）
  -> Mapper 查询条件/排序
  -> API TS 类型（VO/Form/Query）
  -> 页面搜索、表格列、表单项、字典
```

具体类名、注解和分层落点以 `ruoyi6` 与当前源码为准；缺任何实际需要的一环都可能出现“库里有值、接口没有、页面不显示”。无页面、导入导出或后台任务时，不为流程完整性制造无关实现。

### Entity 与 JSONB 绑定

- `@TableName` 绑定真实表，`@TableId` 策略与 DDL 一致；逻辑删除、乐观锁、自动填充和 `MetaObjectHandler` 按当前模块核对。
- 普通 `JacksonTypeHandler` 不能证明 PostgreSQL `jsonb` JDBC 绑定正确。优先复用项目已有的 JSONB-aware TypeHandler，并核对 `autoResultMap`、Entity/BO/VO 类型和 Wrapper 写入链路。
- 项目没有合适处理器时，按 PostgreSQL JDBC 的 `Types.OTHER` / `PGobject` 方式最小适配，不重复造多个处理器。
- 可空字段更新要清空时显式 `.set(field, null)`，不依赖全局更新策略。

### SQL 脚本与字典/参数

- 框架初始化、升级脚本和业务增量分开；业务增量放项目登记目录（RuoYi 默认为 `docs/sql/`），不混入框架升级脚本。
- 生产变更使用增量脚本，不重跑全量初始化；脚本可重复执行或有明确幂等策略。
- PostgreSQL 没有 `DELETE IF EXISTS`；按业务选择条件 INSERT/UPDATE/DELETE 或 `ON CONFLICT`。先删再插可能破坏引用、授权和审计，不作为通用模板。
- DDL 写清主键、非空、默认值、注释、索引和约束。
- 菜单 SQL 用显式 ID 和幂等条件；按钮权限字符与后端注解、前端权限判断一致，具体链路按 `ruoyi6` 核对。
- 字典用 `sys_dict_type` + `sys_dict_data`，参数用 `sys_config`；不为可枚举状态新建业务表，不在页面硬编码字典文本。先查现有类型/键，避免重复造字典和参数。

### 查询、权限与事务

- 先复用项目现有查询入口；复杂联表再沿用 MPJ/XML，不为一张表另造 DAO/Repository。具体 Mapper 继承和分层按 `ruoyi6` 核对。
- 分页在数据库完成；未传 `pageSize` 时限制默认值和上限。空 ID 集合直接返回空结果，不退化为全表查询。
- 关联展示批量查询，避免 N+1；导出复用列表查询条件和数据权限。
- 功能权限和数据权限分开。使用现有数据权限机制，列表、详情、更新、删除和导出覆盖同一范围，SQL 列名与表别名一致。
- 数据范围不得靠前端不展示来保证；关联 ID 和子记录校验可访问性及所属主记录。
- 多表写入明确事务边界和锁顺序；批量写入使用项目已有批处理入口。敏感字段的 VO 脱敏是响应保护，不是数据库访问控制。

## 迁移与执行

迁移评审至少回答：

1. 目标数据库、schema、方言、版本和当前已执行记录是什么。
2. 已有数据多少，新增必填值如何回填；数据回填与 schema 变更是否分开。
3. 是否锁表、重写表、阻塞建索引或启动长事务；大表是否需要分批或在线方案。
4. 新旧代码兼容窗口、发布顺序和切换点。
5. 失败时如何停止、重试、补偿或回滚；不可逆步骤必须如实标注。
6. 孤儿数据、逻辑删除后的唯一性和历史/归档数据如何处理。

PostgreSQL 边界：`CREATE INDEX CONCURRENTLY` 降低阻塞但有自身限制；大表约束可评估先 `NOT VALID` 再 `VALIDATE`；`timestamptz` 与 `timestamp` 语义不同。这些是技术选项，不是执行授权。

读取模型、编写脚本和执行数据库变更是不同授权。连接可用不等于目标正确，也不等于允许写入；未获明确授权时只读取证，不执行 DDL/DML、迁移、清理或带写入的 `EXPLAIN ANALYZE`。

## 工作流接入

触发原则：**只要任务会新增或修改持久化模型（表、列、约束、索引、迁移、字典/参数与数据库字段的绑定），就必须经过本技能。** 需求是否已经明确，只影响是走轻量还是完整准入，不影响是否触发。任务定稿后仍会触发，但不会重新评审产品需求，只核对已批准契约是否正确落地。

| 阶段 | 动作 |
|---|---|
| think | 查库与复用扫描，形成模型选项和推荐；先业务身份与规则，后字段。 |
| grill | 挑战新表必要性，核实唯一性、权限、删除、历史、并发和查询闭环；记录新表审批再冻结。 |
| story | 引用已批准契约与迁移，在纵向切片中承接模型、使用方和验收；不重新发明表。 |
| Direct / implement / debug | 写 DDL 前核对证据、契约和审批；已定稿的小改走轻量增量核对，只写受影响项，不重开需求，也不能绕过准入。 |
| review | 核对实际结构与契约、审批、JSONB 边界、约束、迁移和源码调用；设计建议不自动重构存量。 |

这些阶段由项目和用户按需发起；加载规则不等于自动查全库、修改业务或执行迁移。已批准的任务不应因为加载本技能而重新走一轮需求问答。

## 新表与存量边界

- 新增任何持久化业务表（含关系、历史、导出任务表）前，先列明表名、每行含义、复用/JSONB/加列为何不足、关系与删除行为、增长和查询方式、迁移影响。
- 必须得到用户对**列明的新表**明确同意，才能编写正式建表迁移或依赖该新表的实现；笼统的“开始开发”不等于新表审批。
- 模型批准不等于数据库执行授权；写脚本和执行脚本分开。
- 既有表模型不清时先只读盘点，不一边新增一边大重构；数据库有表但源码不可追溯的，标为治理风险。
- 不因统一风格重写有数据的存量表；业务规则未定又影响数据完整性时，说明缺失证据和当前安全默认，不伪造通过。
- 已批准任务中的简单加字段、补索引或补字典，不要求重新证明“是否需要新表”；但仍要说明复用位置、字段契约、字段链路和迁移影响。

## 交付检查

- [ ] 已扫描现有表、字典、参数和菜单，复用结论有证据。
- [ ] 表角色、一行语义、业务身份和归属明确。
- [ ] 五项准入全部满足；新表有用户明确批准，模型批准与执行授权分开。
- [ ] 生命周期、删除语义、不变量、唯一性和引用行为明确。
- [ ] 主要查询与索引一一对应，或说明扫描在当前规模可接受。
- [ ] JSONB 只用于真正稀疏/可变且不参与关键约束的数据。
- [ ] 字段链路和 Entity/BO/VO/TS 实际受影响项一致。
- [ ] 字典与参数优先复用，DDL 与字典值一致。
- [ ] 迁移覆盖已有数据、兼容窗口、锁风险、幂等和回滚，来源可追溯。
- [ ] 未验证的数据库写入、跨时区行为、存量注释等没有被写成通过。

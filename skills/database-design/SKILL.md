# 数据模型设计

本技能只回答“数据应该怎样建模、已有模型为什么不够、变更怎样迁移”。目标是形成实现可遵循的数据契约，不是直接产出建表脚本。

字段如何落到当前项目的 Java/TS/页面/菜单链路，以及已确认契约的实现核对，由 `ruoyi6/references/database.md` 负责。只有尚未确定模型，或发现已批准契约冲突、关键事实缺失时，才回到本技能。

## 先取证

按任务范围读取：

1. 项目 `AGENTS.md`、已有 PRD、数据模型、决策和迁移记录。
2. 目标数据库的真实 schema、版本、方言、现存表、约束、索引、注释和数据分布。
3. 真实查询、写入、分页、排序、导出、权限和后台任务路径。
4. 需要判断现有实现能否承载时，再查相关源码调用链；不从页面字段反推表结构。

项目专用规则和方言事实只读取适用部分，不另建第二套数据库入口。

## 准入分级

| 变更 | 必做核对 | 不做什么 |
|---|---|---|
| 只读查询或检查现有模型 | 真实 schema、调用链；说明是否命中已有表、字典、参数 | 不生成契约，不要求新表审批 |
| 已批准的普通字段、索引或字典项 | 轻量契约：复用理由、字段语义/类型/可空/默认值、查询依据、迁移与回滚 | 不重做业务判型；源码落点交给 `ruoyi6` |
| 新表、拆并表、关系/唯一性/删除语义/生命周期/历史策略、JSONB 模型或复杂迁移 | 完整契约和五项门槛 | 未批准表名前不写正式建表迁移 |
| 只读 review 或 debug | 核对实际结构与契约、调用链和风险 | 不顺手重构存量，不自动写库 |

普通字段、索引或字典实现不因本技能存在而重新跑一轮建模；一旦改变业务身份、归属、唯一性、状态机、删除或历史保留，升级为完整契约。

## 五项门槛

1. **复用结论**：扫描现有表、列、字典、参数和迁移，说明为什么不能复用或扩展；只写“没有合适的表”不算证据。
2. **表角色与业务身份**：一行代表什么、如何唯一识别、归属谁；一张表只承担一个主要角色。
3. **生命周期与删除语义**：产生、状态迁移、终态、归档/删除、保留期限，以及被引用时怎么办。
4. **不变量与唯一性**：必须永远成立的规则，以及 `NOT NULL`、`UNIQUE`、`CHECK`、外键或事务维护的落点。
5. **迁移与可追溯性**：增量脚本路径、已有数据补值、兼容窗口、失败恢复和回滚依据；找不到创建/迁移来源的新表不能声称完成。

契约写入项目实际使用的 PRD、切片或迁移记录，不新建一套模型文档：

```text
Data Model Contract
- 复用结论
- 表角色、一行语义、业务身份与归属
- 关系与基数；是否允许为空或转移
- 不变量、唯一性与幂等
- 生命周期、状态迁移、删除和保留
- 查询、排序、分页、导出及索引依据
- 容量、并发和锁边界
- 迁移、已有数据、兼容窗口、失败恢复和回滚
- 未决项：待确认什么、当前推荐实现、影响和确认人
```

可用 `scripts/check_model_contract.py` 检查契约字段是否漏写；通过只表示格式完整，不证明模型正确。

需要展开评审顺序、反模式、唯一性/删除细节或结论格式时，读取 [references/model-review.md](references/model-review.md)。

## 建模规则

- **默认不新增表**：页面、菜单、报表、导入、配置项或单个功能都不自动对应一张表。先查现有表、公共字段、字典/参数和关联，能扩展现有模型就不建新表。
- **半结构化 + 宽表优先**：固定列承载身份、归属、唯一键、状态、时间、金额、外键和可查询字段；低频、可选、跨业务差异较大的属性可放入有明确 schema 的 JSONB 半结构化字段。宽表允许适度冗余，但不能把唯一性、状态机、金额、时间或高频筛选字段藏进 JSON。
- **只有语义边界成立才新建表**：现有表无法承载独立实体、可重复明细/多对多关系、独立生命周期/权限/查询边界，或数据库约束确实需要时，才建新表。不能因为“功能独立”“页面独立”“以后可能扩展”就建表。
- **不为未来预建表**：默认不预建主从表、EAV、事件表、版本表、报表表或每个业务域的扩展表；确需拆表时说明当前真实需求、查询和生命周期依据。
- **键与约束**：每张业务表有稳定主键；业务唯一性优先数据库唯一约束，服务层先查后写不能替代并发唯一性。可空性、默认值和 `CHECK` 表达真实规则；引用完整性用外键或明确的事务维护责任。
- **删除与历史**：逐关系明确禁止删除、级联、置空、逻辑删除或归档；不要默认所有表加 `del_flag`。逻辑删除后能否重建同一业务键必须定义；操作日志不等于业务历史。
- **查询与索引**：为主要查询写清过滤、排序、分页和索引依据。外键不自动带索引；低选择性字段不单独建索引；无界 `%keyword%`、导出和批量操作不能假装走索引。
- **JSON**：只承载真正稀疏、结构可变、不参与关键约束或高频连接/排序/聚合的属性，以及外部原始载荷和快照。稳定业务字段、唯一键、状态、金额和关系提升为真实列；明确空值、结构版本和更新语义。

## 迁移与执行

迁移评审至少回答：目标库/schema/方言/已执行记录；已有数据和必填值回填；锁表、重写、阻塞索引和长事务风险；新旧代码兼容窗口与发布顺序；失败停止、重试、补偿和回滚；孤儿数据、逻辑删除和历史数据如何处理。

PostgreSQL 的 `timestamptz` 与 `timestamp` 语义不同；并发建索引、先 `NOT VALID` 再 `VALIDATE` 等只是方言选项，不是执行授权。连接可用不等于目标正确，也不等于允许写入。

读取模型、编写脚本和执行数据库变更是不同授权。未获明确授权时只读取证，不执行 DDL/DML、迁移、清理或带写入的 `EXPLAIN ANALYZE`。

## 新表与存量

- 新增持久化业务表前，列明表名、每行含义、为何不能加列/复用/用 JSON、关系与删除、增长和查询、迁移影响。
- 必须得到用户对**列明的新表**明确同意，才能编写正式建表迁移或依赖该表实现；笼统的“开始开发”不等于新表审批。
- 既有表模型不清时先只读盘点，不一边新增一边大重构；数据库有表但源码不可追溯的，标为治理风险。
- 不因统一风格重写有数据的存量表；规则未定且影响完整性时，说明缺失证据和当前安全默认，不伪造通过。

## 交付检查

- [ ] 复用结论有现有表、字典、参数或迁移证据。
- [ ] 表角色、一行语义、业务身份和归属明确。
- [ ] 五项门槛满足；新表有用户明确批准，模型批准与执行授权分开。
- [ ] 生命周期、删除、唯一性和引用行为明确。
- [ ] 主要查询与索引对应，或说明当前扫描可接受。
- [ ] JSON 只用于真正灵活、低频或原始/快照数据。
- [ ] 迁移覆盖存量数据、兼容窗口、锁风险、幂等和回滚。
- [ ] 未验证的写入、时区、方言行为没有写成通过；源码落点按 `ruoyi6` 核对。

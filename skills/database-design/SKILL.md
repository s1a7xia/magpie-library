# Database Design: Model the Rules Before the Tables

数据库设计的产物不是一个 `CREATE TABLE`，而是能被代码、约束和查询共同维护的数据契约。先确定业务身份、不变量和真实访问路径，再决定表、字段、键和索引。

本技能负责跨阶段的数据建模评审和新增表准入门；RuoYi 的 DDL 落点、Entity/BO/VO/TS 链路、菜单/字典和方言写法仍由 `ruoyi6/references/database.md` 负责。两者同时适用，不互相替代。

## 表准入闸门（强制）

只要任务准备新增表、预建表、临时表以外的业务 schema，或实质改变表关系、唯一性、删除语义、历史保留、索引模型或迁移，就必须先通过本节。它适用于 Direct、Increment、New Module、`think`、`grill`、`story`、`implement`、`debug` 和 `review`；不因为改动小、先写代码方便或“以后再迁移”而跳过。仅增加普通非约束字段、补充注释或执行已经批准且契约完整的 DDL 时，不重复过闸，但仍要核对字段链路和迁移来源。

先写一页以内的 `Data Model Contract`，再动 DDL。以下五项是**硬门槛**，缺任一项都不得写表或提交建表迁移：

1. **复用结论**：扫描现有表、字段、字典、参数、菜单和增量脚本后，说明为什么不能复用或扩展现有模型。只写“没有合适的表”不算证据。
2. **表角色与业务身份**：从核心实体、明细/关系、来源原始事实、规范化结果、派生统计/评分、流程/任务、历史/审计、临时请求/导出中选择角色；说明一行代表什么、如何唯一识别、归属谁。
3. **生命周期与删除语义**：数据从产生到归档/删除的路径、终态、保留期限；删除是禁止、级联、置空、逻辑删除、归档还是注销，被引用时怎么办。
4. **不变量与唯一性**：必须永远成立的业务规则、数据库唯一键/外键/非空/`CHECK` 落点；无法约束的规则说明由哪个事务或服务维护以及如何发现违例。
5. **迁移与可追溯性**：本次 schema 变更对应的增量脚本路径、已有数据补值、兼容窗口、失败恢复和回滚依据。新表没有源码内可追溯的创建/迁移脚本时，不得声称完成；脚本尚未落盘只能标为 `TODO(迁移待落盘)` 并阻塞交付。

契约已写入 PRD、切片或任务记录后，可运行只读检查：

```powershell
python "<本技能目录绝对路径>/scripts/check_model_contract.py" "<契约文件绝对路径>"
```

将上述占位符替换为本 SKILL.md 所在目录及契约的实际绝对路径，不相对项目根目录猜测脚本位置。脚本只检查最小字段是否存在，不判断建模是否正确，也不连接数据库；字段齐全仍需按本技能和项目 schema 做实质评审。

以下内容影响正确性时也必须写入契约，但可由 AI 依据现有事实补全，不必等待用户逐项确认：主要查询与索引、容量与并发、审计历史、字段类型和外部集成边界。

禁止用以下方式绕过闸门：

- 先在开发库建表，再补模型说明或迁移脚本。
- 用“通用表”“万能 JSON”“EAV”“扩展字段”替代明确的业务建模。
- 以代码生成器或 ORM 能跑为由跳过身份、唯一性、删除和索引判断。
- 把建模问题留给后续 PRD、切片或“以后再重构”。
- 把外键缺失当成无需维护引用完整性；必须有补偿检查或明确的清理责任。

### 表角色判定

表角色决定它应有什么约束和生命周期，不应把所有表套成同一种 CRUD 模板。

| 角色 | 一行代表 | 默认重点 |
|---|---|---|
| 核心实体 | 一个独立业务对象 | 稳定身份、归属、状态、唯一键、引用行为 |
| 明细/关系 | 主体下的一条明细或多对多关系 | 复合唯一键、级联/禁止删除、关系属性 |
| 来源原始事实 | 一次外部输入、采集或事件载荷 | 来源幂等键、原始值不可变、去重与重放 |
| 规范化结果 | 从原始事实解析出的标准对象 | 与来源的追溯关系、解析版本、可重算性 |
| 派生统计/评分 | 某个口径、时间窗或版本的聚合结果 | 口径与维度唯一、可重算、过期与重算策略 |
| 流程/任务 | 一次可执行流程、步骤或任务 | 状态机、并发抢占、重试、终态与失败恢复 |
| 历史/审计 | 某对象在某一时点的快照或操作记录 | 只追加、保留期限、查询维度、不可篡改边界 |
| 临时请求/导出 | 一次性请求、异步导出或临时批次 | 过期清理、幂等、结果定位、与正式业务数据隔离 |

同一张表只承担一个主要角色。需要同时承担原始事实和规范化结果、当前状态和历史快照时，先证明合并的必要性；否则拆分并写明关联键。

## 项目模型登记

新表或实质改表在项目已有模型文档时同步登记；项目没有该文档时，在本次 PRD/切片或迁移脚本头部记录同样的信息，不擅自创建新文档体系。最小登记项：

| 项 | 内容 |
|---|---|
| 表与角色 | 表名、主要角色、一句话职责 |
| 身份与归属 | 主键、业务唯一键、归属列和数据范围 |
| 生命周期 | 状态、终态、删除/归档、保留期限 |
| 关系 | 父/子/引用表、基数、删除行为 |
| 查询与索引 | 主要查询入口和索引依据 |
| 迁移来源 | 创建脚本、增量脚本、回滚/补偿位置 |
| 负责人/待确认 | 业务确认人和未决项（如有） |

登记不是重复 DDL；它用于让后来的人回答“这张表为什么存在、谁负责、何时删、从哪里重建”。没有登记的新表视为模型未交付。

## 边界

适用于：

- 新业务表、主从表、关联表、树或状态模型；RuoYi 项目还需按 `ruoyi6/references/database.md` 优先复用现有系统表、字典和参数。
- 新增/修改字段会影响唯一性、可空性、归属、生命周期或历史。
- 需要决定删除语义、审计范围、并发控制、外部单号或幂等键。
- 需要从查询路径推导索引，或评审现有表的可维护性。
- 需要设计或评审增量迁移、回填、兼容和回滚。

不适用于：

- 单纯执行已经批准的 DDL；执行授权和数据库写入风险另按全局规则处理。
- 只查 SQL 语法、ORM 方法或框架类名；先读当前源码和 `ruoyi6`。
- 用外部资料替用户决定未确认的业务规则、权限边界或验收口径。

## 输入

按优先级取证，不凭印象猜表结构：

1. 用户的业务目标、状态、权限、删除和保留要求。
2. 当前项目的 schema、迁移脚本、现有表、字典、参数和菜单。
3. 真实页面、接口、报表和后台任务的查询、筛选、排序、导出与写入路径。
4. 项目 `docs/agents/coding-standards.md`、PRD、ADR、`CONTEXT.md` 和 `docs/research/`。
5. `ruoyi6` 的数据库、后端、能力和作者实现约定。

能由代码、表结构或文档确认的事实自行核实，不向用户询问已经存在的字段或枚举。

## 数据模型契约

涉及新增或实质改变数据模型时，先在 PRD 的 `Technical Approach`、切片的 `What to build` 或当前任务记录中写出以下契约。简单增量可以只写受影响项。

```text
Data Model Contract
- 业务对象与身份：每个实体如何被唯一识别
- 归属与可见范围：用户/部门/组织/租户及数据权限来源
- 业务不变量：必须始终成立、不能只靠页面校验的规则
- 关系与基数：1:1、1:N、N:M；是否允许为空或转移
- 生命周期：状态、合法迁移、终态、失败恢复和历史保留
- 唯一与幂等：业务唯一键、外部单号、导入批次或幂等键
- 删除与引用：物理删除/逻辑删除/归档/注销；被引用时的行为
- 查询与索引：主要查询、筛选、排序、导出及其索引依据
- 容量与并发：行数增长、读写比例、锁与冲突处理
- 迁移与回滚：已有数据补值、兼容窗口、可逆性和失败恢复
- 未决项：待确认什么、当前推荐实现、影响和确认人
```

契约缺失且会影响数据完整性时，不得用“先建表、以后再补”代替决定。能从现有业务和项目约定安全推导的，按推荐实现完成并记录 `TODO(待确认)`；涉及不可逆数据变更、权限扩大或安全风险且没有安全默认值时，停止受影响动作并报告。

## 设计流程

### 1. 先判复用，不先画新表

- 扫描现有系统表、业务表、字典、参数、菜单和增量脚本。
- 用户、部门、角色、岗位、字典、参数、文件优先复用框架已有能力。
- 能加字段、状态或关联解决的，不新建平行业务表。
- 项目已有字典或运行期配置能力时，优先复用，不另建普通业务表；具体表名和接入方式以当前项目规范为准。

### 2. 从不变量和访问路径建模

- 先列实体、身份、归属和关系，再列字段。
- 默认避免重复存储和跨表派生值；反范式必须对应一个明确查询或一致性取舍。
- 需要筛选、排序、连接、唯一或约束的值落真实列，不藏在 JSON 中。
- 记录主要查询及其过滤、排序、分页和数据权限条件；没有查询依据的索引只是猜测。

### 3. 用拆表测试，而不是“未来可能需要”

以下条件至少一项成立时，才拆子表：

- 主体下有可重复的结构化明细。
- 需要数据库约束维护关系完整性。
- 子数据有独立生命周期、权限、查询边界或数据量。
- 不拆会导致无界重复组、空列或无法约束的状态。

普通单表不要预建主从表、通用扩展表、事件表或版本表。明细即使暂时没有独立页面，只要确实重复且需要被约束，也可以建子表。

### 4. 键、类型和约束

- 每张业务表必须有稳定主键；主键策略与项目现有 DDL、Entity 和前端类型一致。
- 业务唯一性优先由数据库唯一约束保证；服务层先查后写不能替代并发唯一性。
- 可空性、默认值和 `CHECK` 约束必须表达真实业务规则；不要把必填只写在表单里。
- 金额使用明确精度的 `numeric`/`decimal`，不使用浮点数。
- 时间类型沿用项目方言约定；如果业务依赖原始时区，另存时区或采用项目已确认的统一策略。
- 字符串长度按真实约束确定，不机械使用 `varchar(255)`。
- 物理外键是否使用由项目现有约定决定；没有物理外键时，必须写清引用完整性由哪个服务、事务或清理任务维护，以及孤儿数据如何发现。

### 5. 删除、历史和并发

- 明确物理删除、逻辑删除、归档或注销，不能同时混用多套语义。
- 逻辑删除要检查唯一约束：删除后是否允许同值重建；必要时用部分唯一索引或项目既有方案。
- 需要恢复、审计或合规留痕时，明确保留期限、操作记录或历史表；`@Log` 不等于业务历史。
- 并发更新需要 `version`、条件更新或锁时，定义冲突返回，不只是加一个字段。
- 批量删除、级联和归档要评估影响行数、锁和失败恢复。

### 6. 从查询推导索引

为范围内的主要查询逐条命名索引，或说明全表扫描在当前规模可接受。至少检查：

- 等值条件、范围条件、排序和分页的组合。
- 复合索引的列顺序；范围列通常放在等值列之后。
- 数据权限、归属或租户列是否应进入索引。
- 逻辑删除和状态过滤是否适合部分索引。
- 唯一约束或主键是否已经提供了同一索引，避免重复。
- 低选择性字段是否单独建索引，写入成本是否值得。
- 模糊查询是否无界，是否真的需要索引大字段。

索引语法按项目实际方言；PostgreSQL 可评估部分索引、表达式索引、`NULLS NOT DISTINCT` 和 `CONCURRENTLY`，但不能把这些当成所有数据库的通用写法。

### 7. 迁移和已有数据

- 生产变更使用增量脚本，不重跑全量初始化。
- 新增 `NOT NULL` 字段先确定已有数据如何补值；不能用无默认值的必填字段直接打生产表。
- 区分 schema 变更与数据回填，明确顺序、批次、可重试性和失败恢复。
- 评估锁、表重写、索引创建和长事务影响；大表不能默认阻塞式操作。
- 迁移要兼容旧代码的读取/写入窗口；需要 expand → migrate → contract 时写清阶段。
- 回滚脚本必须是真实逆操作；无法回滚的破坏性步骤要单独标注，不能假称可逆。
- 脚本可重复执行或有明确幂等策略；执行前核对目标数据库、schema 和已执行记录。

详细检查清单、反模式和 PostgreSQL 相关边界见 [references/model-review.md](references/model-review.md)。

## 接入现有工作流

| 阶段 | 动作 |
|---|---|
| `think` | 方案涉及新表、关系、唯一性、生命周期、索引或迁移时加载本技能，把数据模型契约写入 PRD 技术方案；不要等到编码时才发现模型不成立。 |
| `grill` | 核对已拟模型的身份、生命周期、不变量、查询与新表准入；只向用户确认真正未决的业务决定。 |
| `story` | 切片包含 schema 变更时，要求切片同时承载契约、迁移、使用方和可观察验收标准；不要拆成“先建所有数据库表”的水平切片。只有迁移/修复的独立切片必须说明为何不能与使用方同片落地。 |
| `implement` | 写 DDL 前先读项目现有 schema、增量脚本和 `ruoyi6/references/database.md`；完成表准入闸门，按契约确认键、约束、删除、索引和迁移，再落 SQL 与字段链路。 |
| `debug` | 修复涉及表结构、约束、删除或迁移时同样过闸；不能以“先修通”为由直接改库。 |
| `review` | 数据库变更按本技能检查复用结论、表角色、身份、不变量、约束、引用、删除、索引依据、迁移来源、兼容和已有数据影响；不能只看 SQL 是否能执行。 |

本技能不是新的产品阶段：阶段调用边界、PRD 状态和页面验收仍由项目指令与共享 workflow-contract.md 决定。

## 现行数据库治理

对已经存在但模型不清的表，先做只读盘点，不要一边继续新增一边大重构。盘点顺序：

1. 按表角色分类，标出核心实体、事实、派生、流程、历史和临时表。
2. 检查每张表的主键、业务唯一键、归属、删除语义和外键/补偿关系。
3. 检查源码中是否有创建/增量脚本；数据库有表但源码不可追溯的，列为最高治理风险。
4. 找出双向当前指针、复合外键重叠、无外键引用列、无界派生字段和无过期策略的临时表。
5. 先治理“新增表准入”和“迁移可追溯”，再按业务影响分批整理旧表；不为了统一风格重写有数据的表。

盘点结果写入项目实际使用的模型文档或 PRD/ADR；没有授权时只读，不执行 DDL/DML。

## 停止条件

出现以下情况时，停止受影响的设计或写入，并报告缺什么、当前能确认什么、下一步由谁决定：

- 业务唯一性、删除语义、权限归属或历史保留无法从现有事实推导，且选错会造成不可逆数据错误。
- 需要扩大数据可见范围、跨租户访问或改变安全边界。
- 迁移只能在生产库直接试错，缺少回填、兼容或回滚条件。
- 目标数据库、schema、方言或已执行记录无法确认。
- 新表没有源码内可追溯的创建/增量脚本，且当前任务要求交付 schema 变更。

不要用空表、万能 JSON、通用 EAV、假外键、无界状态字段或“以后再迁移”掩盖未决模型。

## 交付检查

- [ ] 已先扫描现有表和框架能力，复用结论有证据。
- [ ] 表角色、一行语义、业务身份和归属明确，且一张表只有一个主要角色。
- [ ] 表准入闸门的五项硬门槛全部满足，没有用“先建表、以后再补”绕过。
- [ ] 每个实体有身份、归属、生命周期和删除语义。
- [ ] 每个业务不变量都有落库约束或明确的服务层/事务维护位置。
- [ ] 业务唯一性有数据库唯一约束，或有经过确认的替代原因。
- [ ] 关系基数、引用行为和孤儿数据处理明确。
- [ ] 主要查询与索引一一对应，或说明扫描在预期规模可接受。
- [ ] 字段类型、长度、可空性、默认值、注释和审计列符合项目约定。

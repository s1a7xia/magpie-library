# 数据模型评审参考

只在需要展开判断时读取本文件。准入门、RuoYi 落表和授权边界仍以 `SKILL.md` 为准。

## 评审顺序

1. 是否真的需要新表；现有表加字段、状态或关联是否更合适。
2. 表角色、一行语义、业务身份、归属和可见范围。
3. 必须永远成立的规则，以及数据库约束和事务责任的落点。
4. 关系基数、删除行为、生命周期和保留期限。
5. 真实查询、排序、分页、导出和后台任务路径。
6. 数据量、并发、历史和保留期限是否改变模型。
7. 迁移脚本、已有数据、兼容窗口、失败恢复和回滚。

第 1、2、4、5、7 项无法回答时，结论不能是“通过”。“数据库里已经有这张表”不是模型成立的证据。

## 拆表与合并

| 现象 | 优先判断 |
|---|---|
| 主体下有一组可重复、结构稳定的明细 | 子表；明细需要被约束或独立查询 |
| 只是几个固定可选属性 | 同表字段 |
| 需要任意增加属性名 | 先确认是否真是业务元数据；不默认 EAV |
| 字段经常一起读写，没有独立生命周期 | 倾向同表 |
| 子数据有独立权限、状态、归档或大数据量 | 倾向子表 |
| 多对多关系需要额外属性 | 关联表，关系属性放关联表 |
| 只是为未来可能拆而预建子表 | 不拆 |

表数量应来自业务边界和访问方式，不是“越多越规范”。

## 不变量与约束

| 规则 | 首选落点 |
|---|---|
| 单行、单列范围或枚举合法 | `NOT NULL`、`CHECK`、字典值 |
| 跨行或跨表唯一 | `UNIQUE`、复合唯一约束 |
| 引用必须存在 | 物理外键，或明确的服务层/事务维护与孤儿检查 |
| 状态只能按合法路径变化 | Service 状态机 + 条件更新；必要时状态历史 |
| 同一请求只能成功一次 | 业务唯一键或幂等键 + 数据库约束 |
| 金额、数量精度 | `numeric`/`decimal` + 精度和范围约束 |

应用层校验负责友好错误，数据库约束负责最终一致性，两者不能互相替代。`CHECK` 只适合当前行内、稳定、不可变的规则；不要用 `CHECK` 查询其他表。

## 唯一性与删除

评审唯一约束时同时问：

- 空值是否允许重复；PostgreSQL 默认把多个 `NULL` 视为不同，需要“空值也唯一”时显式使用 `NULLS NOT DISTINCT` 或项目既有方案。
- 逻辑删除后同一业务键是否允许重新创建。
- 大小写、前后空格、全角/半角和外部单号是否先规范化。
- 唯一性是否应包含组织或归属列。
- 软删除表的唯一索引是否需要包含删除标记，或改用部分唯一索引。

| 删除行为 | 适用信号 | 风险 |
|---|---|---|
| 禁止删除 | 被引用后必须保留 | 需要可理解的业务错误 |
| 级联删除 | 子数据完全从属且量可控 | 大级联的锁、WAL 和清理成本 |
| 置空引用 | 子数据独立存在 | 页面和报表要能处理空归属 |
| 逻辑删除 | 需要恢复或保留历史 | 查询、唯一约束和清理任务都受影响 |
| 归档/注销 | 保留历史但不能继续使用 | 需明确可查询范围和保留期限 |

不要默认所有表都加 `del_flag` 或 `deleted_at`。没有恢复、审计或引用保留需求的表，物理删除可能更简单。

## 查询与索引

每个主要查询写清：

```text
查询：<页面/接口/报表/任务>
过滤：<等值、范围、数据权限、状态>
排序：<列和方向>
分页：<页码/游标、默认和上限>
索引：<列顺序>，或“扫描在当前规模可接受”
```

复合索引通常等值列在前、范围列在后；排序列是否可用取决于前面的条件。不要只因“字段经常出现在 WHERE”就建单列索引。

需要特别评估：

- 外键引用列是否用于连接、级联或子记录查询；PostgreSQL 不会自动为引用列建索引。
- 数据权限、部门或组织列是否应成为索引前导列。
- 逻辑删除和状态过滤是否适合部分索引。
- 已有唯一索引是否覆盖相同前缀。
- 写入频率高的表是否被过多索引拖慢。
- `LIKE '%keyword%'` 是否有界。
- 导出和批量操作是否绕过分页。

## JSON 与灵活字段

适合：真正稀疏、结构可变、不需要关系约束的属性；外部系统原始载荷或审计快照；不参与高频筛选、排序、连接或唯一性判断的配置。

不适合：用户、部门、状态、金额、时间、外部单号等稳定业务字段；需要 `NOT NULL`、`CHECK`、外键或唯一约束的值；需要频繁筛选、排序、分组、连接或报表聚合的值。

JSON 中的值一旦形成稳定访问路径，优先提升为真实列。GIN 或表达式索引能改善部分查询，但不能恢复普通列约束、外键和完整统计信息。

## 迁移安全

1. 目标数据库、schema、方言、版本和已执行记录。
2. 已有数据量和新增必填值回填。
3. 锁表、表重写、阻塞索引和长事务风险。
4. 新旧代码的兼容窗口和发布顺序。
5. 失败后的停止、重试、补偿和回滚。
6. 生产 DDL 与数据回填是否分开；修复是否可重复执行。
7. 迁移脚本是否与项目现有命名、目录和执行记录一致。

已有数据库但源码没有迁移记录的表，单独立项治理：先确认哪个脚本可重建，找不到就标为不可追溯。PostgreSQL 常见边界：

- `timestamptz` 表示时间点；`timestamp` 是无时区墙上时间。
- `CREATE INDEX CONCURRENTLY` 降低阻塞但有自身限制和失败后的无效索引处理。
- 大表新增约束可评估先 `NOT VALID` 再 `VALIDATE`。
- 标识符默认最长 63 字节；过长会被截断，约束/索引名可能冲突。
- 唯一约束会自动创建唯一 B-tree 索引，不重复建同一索引。

这些是方言提示，不是执行授权。

## 常见反模式

| 反模式 | 问题 | 替代 |
|---|---|---|
| 库里先建表，源码没有创建/迁移脚本 | 无法 review、回滚或重建，环境漂移不可发现 | 增量脚本入库并与使用方同片提交；找不回来源的表登记为治理债务 |
| 每张表都加 `ext1`…`ext10` | 字段语义不可知，无法约束和索引 | 明确字段；真正灵活属性再评估 JSON |
| 万能 EAV 表 | 查询和约束复杂，类型与权限难维护 | 稳定字段用列；确有动态属性的边界单独设计 |
| 用 JSON 存所有业务字段 | 无法约束、连接和高效统计 | 可查询字段提升为列 |
| 只靠服务层保证唯一 | 并发下重复 | 数据库唯一约束 + 友好错误 |
| 所有表都逻辑删除 | 查询和唯一索引复杂化 | 只对确有恢复/审计需求的表使用 |
| 预建未来子表和状态机 | 空结构、错误边界和额外维护 | 当前业务足够的最小模型 |
| 为每个 WHERE 字段建索引 | 写入变慢，索引冗余 | 从完整查询和列顺序推导 |
| 多态外键 | 数据库无法保证引用正确 | 分离表或可约束的多列关系 |
| 物理外键一概禁止且无补偿 | 可能产生孤儿数据 | 明确服务层维护、清理和检查方式 |
| 原始事实、规范化结果、当前状态和历史快照混在一张表 | 生命周期冲突，重算和追溯困难 | 按角色拆表，用来源键和快照键关联 |
| “先建表跑通，以后再设计” | 把建模债务转成数据迁移风险 | 建表前完成五项硬门槛；无法完成就阻塞该 schema 变更 |

## 评审结论

```text
结论：通过 / 有条件通过 / 阻塞

必须修正：
- <问题、触发条件、后果、建议>

可以后续处理：
- <非阻塞优化及理由>

未确认：
- <待确认问题、当前推荐默认、影响、确认人>
```

只报告与本次数据模型风险有关的问题；不要顺手重做无关表或扩大业务范围。

# 数据模型评审参考

本文件只补充 `SKILL.md` 中需要展开的判断。RuoYi 的具体 DDL、字段链路和方言写法仍以 `ruoyi6/references/database.md` 为准。

## 1. 评审顺序

评审一张表或一次迁移时，按以下顺序检查，不要从字段清单开始：

1. 这个对象是否真的需要一张新表；在现有表上加字段、状态或关联是否更合适。
2. 它承担什么表角色，一行代表什么，如何被唯一识别，归属谁，谁可以看到和修改。
3. 哪些规则必须永远成立，违反时系统应拒绝什么。
4. 对象之间是什么基数，删除一方时另一方怎么办，生命周期和保留期限是什么。
5. 页面、接口、报表和后台任务会怎样查询、排序和导出。
6. 数据量、并发、历史和保留期限是否改变模型。
7. 迁移脚本在哪里，如何兼容已有数据和旧代码，失败后如何恢复。

如果第 1、2、4、5、7 项中任一无法回答，结论不能是“通过”。尤其是“数据库里已经有这张表，所以模型成立”不是证据。

字段化契约可用 本技能目录下的 `scripts/check_model_contract.py`（从 SKILL.md 定位后用绝对路径执行） 做只读完整性检查；通过只代表没有漏写字段，不代表模型已经正确。

## 2. 拆表与合并

| 现象 | 优先判断 |
|---|---|
| 主体下有一组可重复、结构稳定的明细 | 子表；明细需要被约束或被独立查询 |
| 只是几个可选属性，数量固定 | 同表字段；不要为每个可选值建子表 |
| 需要任意增加属性名 | 先确认是否真是业务元数据；不要默认 EAV |
| 字段经常一起读写，且没有独立生命周期 | 倾向同表 |
| 子数据有独立权限、状态、归档或大数据量 | 倾向子表 |
| 多对多关系需要额外属性 | 关联表，并把关系属性放在关联表 |
| 只是为“未来可能拆”而预建子表 | 不拆 |

不要把“表越多越规范”当成目标。表的数量应来自业务边界和访问方式，而不是未来假设。

## 3. 不变量与约束

把规则分成三类：

| 规则 | 首选落点 |
|---|---|
| 单行、单列范围或枚举合法 | `NOT NULL`、`CHECK`、字典值 |
| 跨行或跨表唯一 | `UNIQUE`、复合唯一约束 |
| 引用必须存在 | 物理外键，或明确的服务层/事务维护与孤儿检查 |
| 状态只能按合法路径变化 | Service 状态机 + 条件更新；必要时状态历史表 |
| 同一请求只能成功一次 | 业务唯一键或幂等键 + 数据库约束 |
| 金额、数量精度 | `numeric`/`decimal` + 精度和范围约束 |

应用层校验负责给出友好错误，数据库约束负责最终一致性。两者不能互相替代。

`CHECK` 只适合当前行内、稳定、不可变的规则。不要用 `CHECK` 查询其他表；跨表不变量用外键、唯一约束、触发器或明确的事务逻辑。

## 3a. 表角色与反模式

用表角色检查是否把不同生命周期的数据塞进同一张表：

- 核心实体和它的明细通常不应共表；明细有重复结构或独立生命周期时拆开。
- 来源原始事实应保留来源幂等键和原始值，规范化结果应能追溯到来源；把两者混成一张表会导致重放和重算无法解释。
- 派生统计/评分应有口径、时间窗或版本，并能重算；没有这些维度就无法解释历史结果。
- 流程/任务应有状态机、抢占/重试和终态，不要用普通 CRUD 状态字段代替完整生命周期。
- 历史/审计表通常只追加，不当作当前状态表使用；当前指针和历史快照分开。
- 临时请求/导出必须有过期和清理策略，不应无限增长，也不应与正式业务记录混用。

一张表同时出现“原始载荷、规范化字段、当前状态、派生统计、历史快照”中的三类以上时，优先怀疑职责混杂，而不是继续加字段。

## 4. 唯一性与删除

评审唯一约束时同时问：

- 空值是否允许重复？PostgreSQL 默认把多个 `NULL` 视为不同；需要“空值也唯一”时显式使用 `NULLS NOT DISTINCT` 或项目既有方案。
- 逻辑删除后，同一业务键是否允许重新创建？
- 大小写、前后空格、全角/半角和外部单号是否应先规范化？
- 唯一性是否应包含租户、组织或归属列？
- 软删除表的唯一索引是否需要包含删除标记，或改用部分唯一索引？

删除行为必须逐关系写明：

| 行为 | 适用信号 | 风险 |
|---|---|---|
| 禁止删除 | 被引用后必须保留 | 需要可理解的业务错误 |
| 级联删除 | 子数据完全从属且量可控 | 大级联的锁、WAL 和清理成本 |
| 置空引用 | 子数据独立存在 | 页面和报表要能处理空归属 |
| 逻辑删除 | 需要恢复或保留历史 | 查询、唯一约束和清理任务都受影响 |
| 归档/注销 | 保留历史但不能继续使用 | 需要明确可查询范围和保留期限 |

不要默认所有表都加 `del_flag` 或 `deleted_at`。没有恢复、审计或引用保留需求的表，物理删除可能更简单。

## 5. 查询与索引

对每个主要查询写出：

```text
查询：<页面/接口/报表/任务>
过滤：<等值、范围、数据权限、状态>
排序：<列和方向>
分页：<页码/游标、默认和上限>
索引：<列顺序>，或“扫描在当前规模可接受”
```

复合索引通常等值列在前、范围列在后；排序列是否可用还取决于前面的等值条件。不要只因为“字段经常出现在 where 中”就建单列索引。

需要特别评估：

- 外键引用列是否用于连接、级联或子记录查询；PostgreSQL 不会自动为引用列建索引。
- 数据权限、部门、组织或租户列是否应成为索引前导列。
- 逻辑删除和状态过滤是否适合部分索引。
- 已有唯一索引是否已经覆盖相同前缀。
- 写入频率高的表是否被过多索引拖慢。
- `LIKE '%keyword%'` 是否有界；没有合适索引时不要假装它能扩展。
- 导出和批量操作是否绕过分页，是否需要异步或分批。

索引数量不是质量指标；每一个索引都应有查询或约束理由。

## 6. JSON 与灵活字段

JSON 适合：

- 真正稀疏、结构可变、不需要关系约束的属性。
- 外部系统的原始载荷或审计快照。
- 不参与高频筛选、排序、连接或唯一性判断的配置。

不适合：

- 用户、部门、状态、金额、时间、外部单号等稳定业务字段。
- 需要 `NOT NULL`、`CHECK`、外键或唯一约束的值。
- 需要频繁筛选、排序、分组、连接或报表聚合的值。

如果 JSON 中的某个值已经形成稳定访问路径，优先提升为真实列。PostgreSQL 的 GIN 或表达式索引可以提高部分 JSON 查询，但不能恢复普通列约束、外键和完整统计信息。

## 7. 迁移安全

迁移评审至少回答：

1. 目标数据库、schema、方言和当前版本是什么。
2. 已有数据有多少，新增必填值如何回填。
3. 是否会锁表、重写表、创建阻塞索引或启动长事务。
4. 新旧代码能否同时运行；谁先发布，窗口多长。
5. 失败时如何停止、重试、补偿或回滚。
6. 生产 DDL 和数据回填是否分开；数据修复是否可重复执行。
7. 迁移脚本是否与项目现有命名、目录和执行记录一致。

对于已有数据库、但没有源码迁移记录的表，单独立项治理：先确认它在哪个脚本可重建，找不到就标为不可追溯。不要在新增功能里复用“只存在于数据库”的表作为长期基线。

PostgreSQL 常见边界：

- `timestamptz` 表示时间点；`timestamp` 是无时区的墙上时间，不能因为当前用户都在同一时区就默认使用。
- `CREATE INDEX CONCURRENTLY` 降低阻塞，但有自身限制和失败后的无效索引处理，不能机械套用。
- 大表新增约束可考虑先 `NOT VALID` 再 `VALIDATE`，但要确认版本和部署流程支持。
- 标识符默认最长 63 字节；过长会被截断，约束/索引名可能冲突。
- 唯一约束会自动创建唯一 B-tree 索引；不要重复建同一索引。

这些是方言提示，不是项目授权；实际执行前仍按项目配置和数据库变更授权处理。

## 8. 常见反模式

| 反模式 | 问题 | 替代 |
|---|---|---|
| 数据库里先建表，源码里没有创建/迁移脚本 | 无法 review、回滚或重建；环境漂移不可发现 | 增量脚本入库并与代码同片提交；找不回来源的表登记为治理债务 |
| 每张表都加通用 `ext1`…`ext10` | 字段语义不可知，无法约束和索引 | 明确字段；真正灵活属性再评估 JSON |
| 万能 EAV 表 | 查询和约束复杂，类型与权限难维护 | 稳定字段用列；确有动态属性的边界单独设计 |
| 用 JSON 存所有业务字段 | 无法约束、连接和高效统计 | 可查询字段提升为列 |
| 只靠服务层保证唯一 | 并发下重复 | 数据库唯一约束 + 友好错误 |
| 所有表都逻辑删除 | 查询和唯一索引复杂化 | 只对确有恢复/审计需求的表使用 |
| 预建未来子表和状态机 | 空结构、错误边界和额外维护 | 当前业务足够的最小模型 |
| 为每个 WHERE 字段建索引 | 写入变慢，索引冗余 | 从完整查询和列顺序推导 |
| 多态外键 | 数据库无法保证引用正确 | 分离表或可约束的多列关系 |
| 物理外键一概禁止且无补偿 | 可能产生孤儿数据 | 明确服务层维护、清理和检查方式 |
| 把原始事实、规范化结果、当前状态和历史快照塞进同一张表 | 生命周期冲突，重算和追溯困难 | 按角色拆表，用来源键和快照键关联 |
| “先建表跑通，以后再设计” | 把建模债务转成数据迁移风险 | 建表前完成五项硬门槛；不能完成就阻塞该 schema 变更 |

## 9. 评审结论格式

```text
结论：通过 / 有条件通过 / 阻塞

必须修正：
- <问题、触发条件、后果、建议>

可以后续处理：
- <非阻塞优化及理由>

未确认：
- <待确认问题、当前推荐默认、影响、确认人>
```

只报告与本次数据模型风险有关的问题；不要顺手重做无关表或扩大业务范围。

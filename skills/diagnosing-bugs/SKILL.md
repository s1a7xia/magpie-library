# 诊断缺陷

诊断质量取决于是否先有一个**针对用户所说症状**的可靠信号。不要先猜原因、扫代码或连续试命令；先建立并运行这个信号。查证过程中只读探查，测试、修改和提交仍按当前任务授权。

这是一套处理困难缺陷的纪律；只有有明确理由时才跳过阶段，并说明理由。

探查代码库时，读取 `GLOSSARY.md`（如存在）建立相关模块的心智模型，并检查涉及区域的 ADR。

## Codex 执行边界

- 默认由当前 Codex 会话直接诊断和修复，不启动子代理，不创建 worktree，不改变分支。
- Windows 本地命令统一使用 PowerShell 7；需要执行脚本时显式调用 `pwsh -NoLogo -NoProfile -File <脚本路径>`，不要用 bash 语法冒充 PowerShell。
- 测试、构建、启动服务、修改代码、提交和推送分别按当前任务授权执行；“诊断”或“debug”不等于授权新增或运行整套测试。
- 需要人工点击或观察时，先复制并修改 `scripts/hitl-loop.template.ps1`，由当前 Codex 会话运行并读取输出。

## 脱敏

诊断会展示命令、输出和抓取到的材料。**先脱敏每个秘密**：用 `<REDACTED>` 代替。循环应通过环境变量读取凭证，让凭证留在环境中，不进入展示内容。抓取材料可能带有认证头：只引用承载信号的必需行。

脱敏后的输出不足以诊断时，明确说明并请用户补充。

## 第 1 阶段：建立反馈信号

**这是本技能的核心。** 其余步骤都是机械工作。只要有一个**紧密**的通过/失败信号，并且会因_这个缺陷_变红，根因就会被找到；二分、假设验证和插桩都只是消费这个信号。没有它，盯着代码再久也解决不了问题。

在这里投入不成比例的努力：**保持主动，保持创造，不轻易放弃。**

### 建立信号的方式（大致顺序）

1. **失败测试**：在能触达缺陷的 seam 上写单元、集成或端到端测试。
2. **Curl / HTTP 脚本**：对运行中的开发服务器发请求。
3. **CLI 调用**：用固定输入运行命令，把标准输出与已知良好快照对比。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI，并断言 DOM、控制台或网络。
5. **回放抓取轨迹**：把真实网络请求、载荷或事件日志保存到磁盘，再隔离回放到相关代码路径。
6. **一次性测试夹具**：启动最小子系统（单服务、模拟依赖），用一次函数调用走缺陷路径。
7. **属性 / 模糊测试循环**：若缺陷是“有时输出错误”，用大量随机输入寻找失败模式。
8. **二分夹具**：若缺陷出现在两个已知状态（提交、数据集、版本）之间，自动执行“启动状态 X、检查、重复”，以支持 `git bisect run`。
9. **差分循环**：同一输入分别运行旧版与新版（或两种配置），比较输出。
10. **HITL 脚本**：最后手段。必须由人点击时，用 `scripts/hitl-loop.template.ps1` 把人纳入结构化循环，抓取输出再回传。

建立正确的反馈循环，缺陷就解决了 90%。

### 收紧循环

把循环当产品。有了_一个_循环后，继续**收紧**：

- 能更快吗？（缓存准备、跳过无关初始化、缩小测试范围。）
- 信号能更锐利吗？（断言具体症状，而不只是“没崩溃”。）
- 能更确定吗？（固定时间、随机种子、隔离文件系统、冻结网络。）

30 秒且不稳定的循环，比没有循环好不了多少；2 秒且确定的循环才足够紧密，是排障利器。

### 非确定性缺陷

目标不是得到干净复现，而是**提高复现率**。重复触发 100 次、并行、加压力、缩窄时间窗口、注入延迟。能稳定复现 50% 的缺陷可查；1% 的缺陷不可查，因此持续提高复现率直到可查。

### 确实无法建立循环时

停下来明确说明。列出已经尝试的方式，并向用户请求：(a) 能复现问题的环境访问权；(b) 脱敏后的抓取材料（HAR、日志、核心转储、带时间戳的录屏）；或 (c) 添加临时生产插桩的授权。没有循环，**不要**进入假设阶段。

### 完成条件：一个紧密且能变红的循环

第 1 阶段在循环**紧密**且**能变红**时完成：能说出**一条命令**（脚本路径、测试调用、curl），已**至少运行过一次**（展示调用和脱敏输出），并且满足：

- [ ] **能变红**：走真实缺陷代码路径，断言**用户描述的确切症状**，缺陷存在时红、修复后绿。不是“运行不报错”；必须能_抓住这个具体缺陷_。
- [ ] **确定**：每次运行结论一致（不稳定缺陷按上文固定高复现率）。
- [ ] **快**：秒级，而不是分钟级。
- [ ] **Codex 可运行**：能在当前会话无人值守执行；必须人工参与时只用 `scripts/hitl-loop.template.ps1`。

如果在这条命令存在之前就开始读代码建立理论，**停下：直接跳到假设正是本技能要防止的失败模式。** 没有能变红的命令，不进入第 2 阶段。

## 第 2 阶段：复现与最小化

运行循环，观察它随缺陷出现变红。确认：

- [ ] 循环产生的是**用户**描述的失败，而不是附近另一个失败。查错缺陷就等于修错。
- [ ] 失败能跨多次运行复现（非确定性缺陷达到足够高的可查复现率）。
- [ ] 已记录确切症状（报错、错误输出、变慢的时序），供后续阶段判断修复是否真的解决它。

### 最小化

变红后，把复现缩到**仍能变红的最小场景**。一次只删一个输入、调用方、配置、数据或步骤，每删一次就重跑循环，只保留对失败有承重作用的元素。

这样做的原因：最小复现缩小第 3 阶段的假设空间（可疑活动部件更少），并成为第 5 阶段的干净回归用例。

当**剩下的每个元素都承重**时完成：去掉任何一个，循环都会变绿。

必须完成复现**并**最小化，才继续。

## 第 3 阶段：提出可证伪假设

验证前先生成 **3–5 个有排序的假设**。只生成一个假设会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：写出它能作出的预测。

> 格式：“如果 <X> 是原因，那么改变 <Y> 会让缺陷消失 / 改变 <Z> 会让它更严重。”

写不出预测的假设只是感觉：丢弃或锐化。

**验证前把排序列表给用户看。** 用户常有领域知识能立刻重排（“我们刚部署了第 3 项相关改动”），或知道哪些假设已被排除。这个检查点成本低、收益高；用户不在时不要阻塞，按你的排序继续。

## 第 4 阶段：定向取证

每个探测必须对应第 3 阶段的某个具体预测。**一次只改变一个变量。**

工具优先顺序（Windows 本地环境）：

1. 环境支持时，用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能区分假设的边界加**定向日志**。
3. 不“记录一切再 grep”。

**给每条调试日志加唯一前缀**，如 `[DEBUG-a4f2]`。收尾时用 `rg -n '\[DEBUG-'` 或 `Select-String` 就能清理。没有标记的日志会留下来，有标记的能清掉。

**性能分支**：性能回归中日志通常是错的工具。先建立基线测量（计时夹具、`performance.now()`、性能剖析、查询计划），再二分。先测量，后修复。

## 第 5 阶段：修复与回归证据

写回归测试前，先确认当前任务是否明确授权新增或运行测试。未授权时，用第 1 阶段的可重复信号、复现步骤和修复前后的观察结果作为证据，不擅自新增测试或运行测试套件。

只有在测试已获授权，并且存在**正确 seam** 时才写回归测试。

正确的 seam 是测试能走**真实缺陷模式**、与调用点一致的位置。若唯一可用的 seam 太浅（多调用方缺陷只测单调用方，单测无法复制触发链），在那里写回归测试只会制造虚假信心。

**没有正确 seam 本身就是发现。** 记下来：现有代码架构阻止了这个缺陷被锁定，并把它留给下一阶段处理。

如果已有测试授权且存在正确 seam：

1. 把最小复现转成该 seam 上的失败测试。
2. 观察它失败。若是通过改代码或夹具强制变红，先与原始副本 `diff`，证明改动确实生效，再相信结果。
3. 应用修复。
4. 观察它通过。
5. 用第 1 阶段循环重跑原始（未最小化）场景。

## 第 6 阶段：清理

宣布完成前必须：

- [ ] 原始复现不再出现（重跑第 1 阶段循环）
- [ ] 回归测试通过（已授权且存在 seam 时），或已写明未验证/无合适 seam 的原因
- [ ] 所有 `[DEBUG-...]` 插桩已移除（用 `rg` 或 `Select-String` 核对）
- [ ] 一次性原型已删除，或移到明确标记的调试位置
- [ ] 给用户的结论写明最终成立的根因假设；需要提交时，再由获授权的提交说明记录

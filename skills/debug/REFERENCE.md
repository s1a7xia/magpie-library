# Debug — 证据、系统定位与可选模式

## 上下文与快速定位

按 [入口协议](../rules/entry-protocol.md) 加载相关配置/profile 与当前代码，不因有 Java/React/SQL 就强制 RuoYi。缺领域文档时可从调用链诊断并说明限制，不自动初始化项目。

先记录实际症状、期望结果、发生条件、最近变化和原始错误。形成 1–2 个能解释相关症状的假设，用已有日志、堆栈和代码数据流核实；不能只凭报错位置改症状。证据足够则直接最小修复，不强制进入完整六阶段或增加日志。

RuoYi 菜单、字典、参数或权限出现“库里已改、页面未生效”时，按 [缓存与生效诊断](../ruoyi6/references/capabilities.md#缓存与生效诊断) 取证；不是通用 debug 的强制步骤，也不授权清缓存、踢用户或重启。

## 六阶段（仅复杂缺陷需要）

### Phase 1 — 选择反馈信号

优先用户提供的准确步骤、已有失败结果、当前日志和项目已有复现目标。读取代码可建立可证伪假设，不要求先运行。只有获当前请求授权才运行已有测试、HTTP/CLI 或浏览器复现；新增回归测试须另有编写测试授权。数据写入、生产探针、压力/模糊测试、容器与新框架不随 debug 自动获批。

信号要区分当前缺陷与附近另一错误。间歇性问题先核对时间线、版本和并发边界，不默认执行 100 次压力或随机循环。跨环境只比较相关配置，脱敏后记录；不导出全量环境变量或凭证。

### Phase 2 — 确认症状

有运行授权和可用环境时复现并保留准确结果。否则继续静态诊断，区分“用户报告”“日志证据”“静态推断”和“代理实测”。若关键证据无法从现有材料获得，给最小复现指南：步骤、预期/实际、所需日志；只停依赖该证据的部分。不把不能运行误称无缺陷，也不把静态修复称运行已恢复。

### Phase 3 — 可证伪假设

按现有证据排序少量假设，写出各自预测与反证条件；不用固定凑够数量或每轮让用户批准。新增证据改变假设才换方向，已被反证的路径不重复尝试。

### Phase 4 — 必要探针

已有证据不足时，按授权添加最少临时日志或断点，探针对应具体预测，一次只改变一个关键变量。日志脱敏，异步问题记录序列/时间；只需要时持久化到本任务临时文件，记下归属，不能记录令牌/隐私。只读诊断不修改源码加日志。

连续 3 个已被反证的假设仍无法定位时停止试错，交付已排除项、原始错误、未知与下一条所需证据；不自动委派或转入 research。

### Phase 5 — 最小修复与回归保护

修复实际根因，检查相关调用与边界，不顺手改 UI 设计或不相关架构。只有当前请求明确授权新增/修改测试时才建立针对性回归测试，使用现有正确接缝；仅获运行授权则只跑已有目标。无合适接缝时报告缺口，不造框架。旧代码失败/新代码通过只能在实际观察后声明。

### Phase 6 — 收尾与交接

核对最终 diff、相关调用关系，记录已执行与未执行检查。只删除本任务明确创建的探针和临时文件，不能递归删除整个既有 `DEBUG/`。需要保留的复现证据先脱敏并按用户/项目要求归档。更新适用状态与失效证据，Git 按既有授权；返回 review/page-acceptance 调用点，不自动启动新产品阶段。

## 可选：Bisect

“以前正常”先用相关 `git log`/diff 缩小范围，不自动运行二分或测试。运行二分需有实际可重复且已授权的检查、可证明的 good/bad 提交；最新 tag 不代表 good。

确需二分且 Git/worktree 操作获授权时，始终在独立临时 detached worktree 执行，绝不 checkout/reset 用户当前工作区，清洁工作区也一样。无法隔离则报告，不要求 stash/clean。记录 worktree 绝对路径、good/bad、检查命令；结束在临时 worktree `git bisect reset`，按归属和路径核对后清理自己创建的 checkout。不删除已有或其他会话 worktree。

## 可选：Scope scan

修复后只读检查直接调用方、共享实现及同一受影响数据流。用户要求查同类时再扩大到相关模块，排除生成物/依赖/构建目录，不强制全库扫描。报告相似项是否同因；不相关缺陷仅报告，除非用户授权，不批量修复。

## 交付证据

根因位置与机制、修改范围、证据来源、授权检查结果、静态/运行边界、未验证回归风险。没有运行证据时可交付代码修复，但只能写“已修复代码，运行未验证”，不能声称原复现已通过。
